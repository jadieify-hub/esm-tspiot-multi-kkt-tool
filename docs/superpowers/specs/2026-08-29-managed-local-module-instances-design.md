# Управляемые экземпляры ЛМ ЧЗ для нескольких ККТ

**Статус:** скорректировано по архитектурному ревью 2026-08-29; ожидает повторного подтверждения перед планом реализации.

**Целевая версия ЛМ ЧЗ:** `regime-2.6.1-7.msi` / ProductVersion `2.6.1`.

**Связанная спецификация:**

- `docs/superpowers/specs/2026-08-26-multi-inn-lm-gateways-design.md` — экземпляры ЕСМ, контроллеры ЛМ ЧЗ и привязка к ЕСМ.

Эта спецификация расширяет прежний объём работ: исключение, запрещавшее установку и обновление самого ЛМ ЧЗ, больше не действует для управляемых экземпляров, описанных ниже. Лицензионная граница вместо этого зафиксирована в разделе 4. Остальные ограничения и проверки безопасности связанной спецификации сохраняются.

## 1. Задача

На одном компьютере могут работать одна или несколько физических ККТ, в том числе принадлежащих разным ИНН. Для каждого уникального ИНН в рамках этой торговой точки нужен отдельный полностью изолированный экземпляр ЛМ ЧЗ. Каждая ККТ получает отдельный контроллер ЛМ ЧЗ. Если у всех ККТ разные ИНН, как в исходном сценарии владельца проекта, это даёт ровно один ЛМ на каждую ККТ.

Обычный пользовательский сценарий должен выполняться одним запуском автоматической настройки:

```text
физическая ККТ
  -> экземпляр ККТ в ЕСМ
  -> ЛМ ЧЗ для ИНН этой ККТ
  -> отдельный контроллер этой ККТ
  -> привязка контроллера к экземпляру ЕСМ
```

Пользователь выбирает официальный MSI ЛМ ЧЗ и официальный установщик контроллера. После подтверждения программа самостоятельно создаёт все необходимые экземпляры, назначает порты, запускает службы и показывает итог по каждой ККТ.

Инициализация ЛМ ЧЗ не входит в задачу. Её выполняет ЕСМ либо сторонняя утилита. Программа не открывает браузер и не показывает ссылки для инициализации.

## 2. Термины и границы подсистем

- **ККТ** — физическая касса, однозначно определяемая серийным номером; ИНН является обязательным атрибутом строки.
- **Экземпляр ЕСМ** — существующая управляемая запись ККТ в ЕСМ/ТС ПИоТ.
- **Общий runtime ЛМ** — одна защищённая read-only копия неизменённых исполняемых файлов официального ЛМ для одной точной версии MSI. Он не содержит данных конкретного ИНН.
- **Управляемый ЛМ** — отдельный запущенный экземпляр для одного ИНН, использующий общий read-only runtime, но имеющий собственные конфигурацию, каталог данных, журналы, порты, Erlang-кластер и пару процессов `yenisei`/`regime`.
- **Управляемый контроллер** — уже реализованный отдельный экземпляр контроллера ЛМ ЧЗ, который подключается к соответствующему управляемому ЛМ.
- **Комплект ККТ** — одна строка связи `ККТ -> ЕСМ -> ЛМ -> контроллер`.
- **Владение** — подтверждённая manifest и журналом принадлежность службы, каталога и конфигурации этой программе.

Первый ЛМ не является штатной установкой и не имеет особого режима. Все управляемые ЛМ, включая №1, создаются и обслуживаются одинаково. Несколько ККТ одного ИНН в этой торговой точке ссылаются на один управляемый ЛМ, но имеют разные контроллеры. Существующие штатные службы `regime` и `yenisei` не назначаются ККТ, не перенастраиваются и не удаляются автоматически.

## 3. Подтверждённые свойства официального MSI

Исходный пакет предоставлен пользователем и исследован статически и через административное извлечение без установки служб на рабочий компьютер.

| Свойство | Значение |
| --- | --- |
| Файл | `regime-2.6.1-7.msi` |
| Размер | `51 007 488` байт |
| SHA-256 | `68a9633cefc912c2c1defae40d1c8f433bb794ee66060b822f0895410ab6c5c6` |
| ProductName | `Локальный модуль Честный Знак` |
| ProductVersion | `2.6.1` |
| ProductCode | `{556FD8AD-43A3-4645-BC54-EBF3043ADF82}` |
| UpgradeCode | `{9449123B-61C4-40DE-AA6C-1BB9AA02EB67}` |
| Подписант | ООО «Центр развития перспективных технологий» |
| Authenticode | действителен на дату исследования |

Пакет штатно использует:

- один каталог `Program Files\Regime`;
- фиксированные службы `yenisei` и `regime`, создаваемые через вложенный `nssm.exe`;
- фиксированные записи реестра установки;
- порт API ЛМ `5995`;
- порт локальной базы `5984`;
- Erlang-узлы `regime@127.0.0.1` и `yenisei@127.0.0.1`;
- отдельный установщик автообновления `InstallAutoUpdateLM.exe`.

Поэтому повторный штатный запуск MSI не создаёт независимый экземпляр. Встроенный автообновлятор также не подходит для нескольких управляемых каталогов и не устанавливается программой.

## 4. Лицензионная граница

ЛМ ЧЗ предоставляется ООО «Оператор-ЦРПТ» на условиях безвозмездной открытой лицензии; работы по его установке и настройке в безвозмездное предоставление самого ПО не входят. Типовая форма утверждена приказом Минпромторга России от 03.02.2025 № 449. Пункт 1.1 разрешает воспроизведение, инсталляцию, запуск, хранение, копирование, активацию, обновление и использование ЛМ в составе иных программ. Пункты 2.7.2–2.7.3 запрещают переработку/модификацию программы и передачу лицензионных прав третьим лицам вне предусмотренного исключения.

Официальная техническая рекомендация требует один экземпляр ЛМ на торговую точку в рамках одного ИНН независимо от числа касс; для каждого ИНН нужен отдельный экземпляр. Поэтому число управляемых ЛМ равно числу уникальных ИНН среди выбранных ККТ, а не безусловно числу ККТ. Лицензия контроллера ЛМ ЧЗ на каждую ККТ является отдельным вопросом и не используется как обоснование для развёртывания самого ЛМ.

Инженерная граница:

1. Пользователь сам предоставляет официальный MSI. Программа не загружает и не распространяет ЛМ, а MSI и извлечённые vendor-файлы не попадают в Git, CI или релиз.
2. Vendor-бинарники, boot-файлы и библиотеки не изменяются, не переименовываются, не перепаковываются и не переподписываются. App-owned конфиги и каталоги данных создаются отдельно и не подменяют файлы официального runtime.
3. Лицензионные проверки, активация, инициализация, привязка и ограничения ЛМ не обходятся, не отключаются, не эмулируются и не подделываются.
4. Административное извлечение и копирование опираются на прямо предоставленные права воспроизведения, инсталляции и копирования. Поэтому выбор между общим runtime и копией runtime на экземпляр является техническим решением; повторное лицензионное решение для fallback не требуется.
5. Максимальное число управляемых ЛМ ограничено числом уникальных ИНН в подтверждённом списке ККТ. Программа не создаёт ЛМ «про запас».

Вывод раздела опирается на опубликованную типовую форму и официальные материалы «Честного знака»; это инженерная граница, а не юридическое заключение. Отсутствие ответа правообладателя не блокирует private-реализацию. Перед возвратом этой части в public повторно проверяются актуальные условия лицензии, публикационная граница и наличие vendor-файлов в поставке.

Источники: [пункт 1.1 типовой лицензии](https://www.consultant.ru/document/cons_doc_LAW_510982/e6d477cd68e197fe169e6c9c750a87dc9c195e76/), [пункты 2.7.2–2.7.3](https://www.consultant.ru/document/cons_doc_LAW_510982/89857e8a5b2389da1d4b1bf190e0126ee030a835/), [официальное описание лицензии ЛМ](https://markirovka.ru/knowledge/tovarnye-gruppy/obschie-voprosy-gis/chto-takoe-po-lokalnyy-modul-chestnyy-znak-%29), [один ЛМ на торговую точку и ИНН](https://markirovka.ru/knowledge/tovarnye-gruppy/obschie-voprosy-gis/vozmozhno-li-postavit-lokalnyy-modul-chestnyy-znak-na-neskolko-magazinov-obedinennykh-lokalnoy-setyu).

## 5. Выбранный способ развёртывания

Программа не изменяет MSI, его CAB-потоки или исполняемые файлы. Для каждой поддерживаемой версии используется следующий процесс:

1. Проверить MSI без повышения прав: формат, ProductName, ProductVersion, обязательные таблицы и файлы, Authenticode-подпись и подписанта.
2. Рассчитать SHA-256 и показать пользователю имя, версию, подписанта и сокращённый хэш.
3. Перед изменением системы скопировать MSI в защищённый staging-каталог.
4. Повторно проверить размер, хэш и подпись staging-копии.
5. Выполнить административное извлечение фиксированной командой Windows Installer с `/a` и `/qn`; пользовательские параметры командной строки не принимаются.
6. Проверить структуру извлечённого образа и хэши обязательных файлов.
7. Скопировать runtime-часть образа **один раз для точной версии** в общий защищённый read-only каталог. Административный MSI, ярлыки, `nssm.exe` и `InstallAutoUpdateLM.exe` в управляемый runtime не входят; содержимое остальных vendor-файлов не изменяется.
8. Для каждого уникального ИНН самостоятельно создать только app-owned конфигурацию, каталоги данных/журналов и записи служб, принадлежащие программе.
9. Удалить staging после завершения или записать состояние `CleanupPending`, если файлы временно заняты.

Преимущества этого способа:

- исходная подпись и хэш MSI проверяются до использования;
- не требуется менять ProductCode, UpgradeCode и более двух тысяч MSI-компонентов;
- все экземпляры имеют одинаковый жизненный цикл, но не дублируют бинарный runtime;
- полное удаление и повторная установка не зависят от Windows Installer product registration;
- vendor-бинарники не попадают в Git и компактную поставку программы.

## 6. Каталоги и права

Каждый комплект ККТ получает стабильный идентификатор по нормализованному серийному номеру ККТ и ИНН. Управляемый ЛМ получает отдельный стабильный instance-id по нормализованному ИНН и сохранённому ownership nonce; текст пользователя в имена путей и служб не попадает.

Рекомендуемая структура:

```text
%ProgramFiles%\KRS\MultiKKT\LocalModuleRuntime\<version-id>\
%ProgramData%\KRS\MultiKKT\LocalModules\<instance-id>\manifest.json
%ProgramData%\KRS\MultiKKT\LocalModules\<instance-id>\config\
%ProgramData%\KRS\MultiKKT\LocalModules\<instance-id>\data\
%ProgramData%\KRS\MultiKKT\LocalModules\<instance-id>\logs\
%ProgramData%\KRS\MultiKKT\LocalModules\<instance-id>\operations\
```

Общий runtime неизменяем и доступен service SID только на чтение и запуск. Все изменяемые конфиги, базы, key-store и журналы находятся в отдельном профиле ИНН под `ProgramData`. Обычные пользователи не получают права изменения runtime или профилей. Запуск из общего runtime разрешается только после VM-проверки всех относительных путей версии `2.6.1-7`. Если изоляция из общего runtime невозможна, capability-профиль разрешает технический fallback к отдельной неизменённой копии runtime на ИНН.

Во всей цепочке путей запрещены symlink, junction, mount point и другие reparse point. Перед копированием, запуском, обновлением и удалением выполняется повторная проверка нормализованного абсолютного пути и владельца manifest.

## 7. Стабильная нумерация и порты

Номер комплекта ККТ `K` назначается один раз и сохраняется по точному ключу `серийный номер ККТ + ИНН`. Номер ЛМ `N` назначается один раз по уникальному ИНН. При первом появлении ИНН `N` по возможности берётся равным `K` первой его ККТ. Если другая ККТ имеет тот же ИНН, она сохраняет свой `K`, но использует уже назначенный ЛМ и его `N`.

Сортировка таблицы или временная недоступность ККТ не перенумеровывает существующие комплекты и ЛМ. После полного удаления номер можно повторно использовать только если относящиеся к нему службы, каталоги и порты освобождены. Поддерживаемый диапазон — `K` и `N` от 1 до 32.

Для номеров `K` и `N`:

- API ЛМ: `4995 + 1000 * N`;
- база ЛМ: `4984 + 1000 * N`;
- EPMD конкретного ЛМ: `43690 + N`;
- gRPC контроллера: `45000 + K`;
- REST контроллера: `15000 + K`.

Примеры:

| № | API ЛМ | База ЛМ | gRPC контроллера | REST контроллера |
| ---: | ---: | ---: | ---: | ---: |
| 1 | 5995 | 5984 | 45001 | 15001 |
| 2 | 6995 | 6984 | 45002 | 15002 |
| 3 | 7995 | 7984 | 45003 | 15003 |

По умолчанию все слушатели доступны только на `127.0.0.1`. Все пулы по умолчанию оканчиваются ниже стандартного динамического TCP-диапазона Windows `49152–65535`. Ручное изменение адресов и портов остаётся доступно в расширенных параметрах до создания экземпляра. Занятый или недопустимый порт блокирует конкретную строку; программа не делает скрытый сдвиг, нарушающий соответствие номеру.

Переход gRPC-пула контроллеров с ранее спроектированных `55001–55032` на `45001–45032` является явной миграцией контракта проекта. Перед включением управляемых ЛМ синхронно обновляются `LmGatewayDraftDefaults`, подписи `авто` в UI, README, связанная спецификация и тесты обоих target framework и helper. Уже созданный профиль с явно сохранённым портом `550xx` не перенумеровывается молча: программа либо сохраняет и повторно проверяет этот порт как legacy-настройку, либо предлагает отдельное подтверждённое пересоздание. Новые и заново создаваемые профили получают только пул `45001–45032`.

EPMD-порт является внутренним и в основной таблице не показывается. Для обеих служб одного ЛМ задаются process-local `ERL_EPMD_PORT` и `ERL_EPMD_ADDRESS=127.0.0.1`. Это создаёт независимый Erlang-кластер для каждого ИНН. Любой запущенный helper вызов `erl`, `epmd` или другого Erlang-инструмента обязан получить тот же `ERL_EPMD_PORT`; запросы `epmd -names` и `epmd -kill` дополнительно получают явный `-port <N>`. Вызов без этого контекста запрещён. Такой режим предусмотрен [официальной документацией Erlang](https://www.erlang.org/doc/apps/erts/epmd_cmd.html): разные EPMD-порты позволяют независимым кластерам сосуществовать на одном компьютере.

Проверка свободных портов выполняется при построении плана и непосредственно перед запуском. После запуска listener PID должен принадлежать ожидаемому процессному дереву соответствующей службы.

## 8. Генерация конфигурации

Официальные `.dist`, `sys.config`, `vm.args` и `erl.ini` в общем runtime остаются read-only и не изменяются. Из проверенных шаблонов capability-профиль `2.6.1-7` создаёт в профиле ИНН отдельные app-owned файлы:

- `regime-local.ini`: loopback-адрес, API-порт, URL соответствующей базы и абсолютный key-store path;
- `yenisei-local.ini`: loopback-адрес, DB-порт и абсолютные каталоги базы, индексов и журнала;
- два `vm.args`: уникальные имена Erlang-узлов и общий только для данной пары cookie;
- два `sys.config`, которые ссылаются на app-owned `local.ini` и абсолютные журналы конкретного ИНН.

Прямой запуск `erl.exe` получает абсолютные `-args_file` и `-config` конкретного профиля. Рабочий каталог и `ERL_LIBS` указывают на общий runtime; query-server paths задаются абсолютными process-local переменными. Общий `erts-*/bin/erl.ini` не содержит путей конкретного ИНН и не изменяется.

Неизвестный формат, отсутствие секции, дублирование обязательного ключа или несовпадение структуры блокирует создание экземпляров. Поиск и замена произвольного текста не используются.

Пароли, сертификаты, токены и данные инициализации не копируются из другого ЛМ и не запрашиваются программой. Каждый экземпляр начинает с отдельной пустой базы и состоянием `Готов к инициализации`.

До включения общего runtime в capability-профиль одноразовая VM должна подтвердить одновременную работу не менее двух пар `yenisei`/`regime` из одного read-only runtime, отсутствие записи в runtime и разделение конфигов, баз, key-store, журналов, node names и EPMD. Отдельно сверяются итоговые `vm.args`, `sys.config` и process-local окружение. При неуспехе общий runtime не признаётся совместимым; fallback к отдельным копиям требует своего точного capability-профиля и повторного VM-прогона.

## 9. Службы и порядок запуска

Один логический ЛМ состоит из двух управляемых служб с собственными именами проекта:

- служба базы, запускающая извлечённый `yenisei`;
- служба API, запускающая извлечённый `regime`.

Имена SCM не повторяют имена и шаблоны сторонней утилиты. Они выводятся из собственного префикса проекта и стабильного instance-id. Человекочитаемые DisplayName содержат номер ЛМ и ИНН; список связанных ККТ доступен в технических деталях, но не включается в SCM-имя.

Службы создаются нативным SCM-механизмом helper через Windows API. Хостом службы является собственный подписанный `EsmTspiot.ServiceProvisioner.exe`, а не `nssm.exe`. Существующие низкоуровневые `LmGatewaySupervisorService` и `LmControllerChildProcess` рефакторятся в общий типизированный service host и нативный child runtime. Инвариант контроллера «пустые аргументы» не ослабляется: для ЛМ вводится отдельный тип start plan с фиксированными токенами capability-профиля.

Каждая служба запускает свой `erl.exe` напрямую через `CreateProcessW`, без batch, PowerShell, `cmd.exe`, `sc.exe` и пользовательских аргументов. API-служба имеет явную SCM-зависимость от DB-службы. Обе службы имеют restricted service SID и получают только необходимые ACL.

Поскольку все экземпляры используют один путь `erl.exe`, один только InstallRoot и хэш бинарника не доказывают владение конкретным экземпляром. Точная идентичность доказывается совокупностью: SCM-служба и её restricted SID, PID дочернего процесса и его parent PID, точный хэш/путь runtime, абсолютный путь app-owned конфига в фактической командной строке, номер EPMD в process environment, manifest nonce и listener PID. После каждой операции helper независимо перечитывает SCM, процессы, командные строки и слушатели.

Порядок запуска:

1. запустить службу базы;
2. дождаться состояния Running, ожидаемого process tree и слушателя DB-порта;
3. запустить службу API;
4. дождаться состояния Running, ожидаемого process tree и слушателя API-порта;
5. присвоить логическому ЛМ состояние `Готов к инициализации`;
6. только затем запускать соответствующий контроллер и привязку к ЕСМ.

Остановка выполняется в обратном порядке. После остановки обоих Erlang-узлов helper обращается только к EPMD-порту этого экземпляра, убеждается, что список узлов пуст, и штатно завершает его. Отказ `epmd -kill` при живых узлах — ожидаемый заблокированный исход `CleanupBlocked`, а не ошибка для автоповтора. `ERL_EPMD_RELAXED_COMMAND_CHECK`, `epmd -stop` и общий `taskkill /IM epmd.exe` запрещены. Аварийное завершение одного дочернего процесса переводит весь логический ЛМ в ошибку; попытка автоматического бесконечного перезапуска внутри UI не выполняется. Ограниченное восстановление оставляется политике SCM и явно отображается в журнале.

## 10. Manifest и журнал операций

Модель владения разделена на три уровня и не содержит секретов.

Manifest общего runtime включает schema version, ProductName/ProductVersion/ProductCode/UpgradeCode, размер и SHA-256 MSI, подписанта, корневой путь runtime, хэши обязательных vendor-файлов, capability id, ownership nonce и счётчик подтверждённых ссылок на профили ИНН.

Manifest управляемого ЛМ включает:

- ИНН, стабильный номер ЛМ и instance-id;
- ссылку на exact-version runtime manifest;
- абсолютные пути профиля, конфигов, данных и журналов;
- API/DB/EPMD-порты, имена Erlang-узлов и имена обеих SCM-служб;
- хэши app-owned конфигов, ownership nonce, текущее состояние и последнюю завершённую операцию.

Запись комплекта ККТ включает серийный номер, ИНН, номер `K`, ссылку на LM instance-id, идентификатор записи ЕСМ и имя/порты собственного контроллера. Удаление одной ККТ не даёт права удалить общий для других ККТ ЛМ.

Каждая изменяющая операция имеет operation journal с контрольными точками. После сбоя питания или перезагрузки программа не начинает установку заново вслепую, а сначала сверяет журнал, manifest, SCM, файлы, процессы и слушатели.

Повторный запуск идемпотентен: существующий корректный комплект подтверждается, неполный — достраивается или предлагается к очистке, чужой или неоднозначный — не изменяется.

## 11. Автоматический сценарий

При старте автоматической настройки программа запрашивает отсутствующие файлы:

1. официальный MSI ЛМ ЧЗ;
2. официальный установщик контроллера ЛМ ЧЗ.

До первого изменения строится единый план для всех найденных ККТ и групп уникальных ИНН. Один подтверждённый запуск разрешает всю последовательность и один пакетный запрос UAC. Привилегированный helper остаётся жив на всём поэтапном выполнении; отдельный UAC для каждой строки не появляется.

Порядок обязательно содержит canary-этап:

1. проверить оба пакета, runtime-профиль, порты и все глобальные условия до мутаций;
2. выбрать первую валидную ККТ первого уникального ИНН как canary;
3. только для canary пройти всю цепочку `регистрация ККТ в ЕСМ -> ЛМ для ИНН -> контроллер ККТ -> привязка/read-back`;
4. подтвердить SCM-определения, process tree, конфиги, DB/API/EPMD/listener ownership, состояние «Готов к инициализации» и доступный ответ ЕСМ;
5. только после успешного canary последовательно обработать оставшиеся ККТ того же ИНН, а затем остальные группы ИНН;
6. показать сводку по всем строкам и группам ИНН.

Глобальная ошибка пакета, staging или безопасности останавливает сценарий до изменений. Ошибка canary останавливает все ещё не начатые строки; они не регистрируются даже в ЕСМ. После успешного canary ошибка одной последующей ККТ не мешает завершить независимые строки других ИНН. Следующий этап конкретной строки не запускается, если предыдущий неуспешен. Если ошибка показала общий дефект runtime/capability, останавливаются все оставшиеся группы.

Пользователь может закрыть итоговый диалог, но журнал операции сохраняется. Завершение автоматического сценария не означает завершённую бизнес-инициализацию ЛМ: честный успешный статус до неё — `ЛМ запущен, готов к инициализации`.

## 12. Интерфейс

Существующая вкладка контроллеров преобразуется в пользовательскую вкладку `ЛМ ЧЗ`. Техническая разница между базой, API и контроллером остаётся во внутренней модели и журнале, но не загромождает основную таблицу.

Верхняя часть содержит два компактных селектора:

- `Установщик ЛМ ЧЗ`;
- `Установщик контроллера`.

Основная таблица содержит только:

- № ККТ;
- серийный номер;
- ИНН;
- порт кассового ПО из ЕСМ;
- адрес и порт ЛМ ЧЗ одной строкой;
- состояние ЛМ;
- состояние связи с ЕСМ.

Внутренний DB-порт, gRPC/REST контроллера, имена служб, пути и хэши не показываются постоянными колонками. Они доступны в раскрываемых технических деталях и журнале.

Если несколько строк ККТ имеют один ИНН, в основной таблице у них честно повторяются endpoint и состояние общего ЛМ, но порт кассового ПО и состояние связи с ЕСМ остаются индивидуальными. Технические детали показывают номер ЛМ и список всех связанных ККТ.

Адреса и порты предзаполняются. Обычному пользователю достаточно выбрать пакеты и нажать запуск. Редактирование доступно в блоке `Дополнительные параметры` до создания экземпляра.

Никакие URL автоматически не открываются и не оформляются как призыв перейти к инициализации.

## 13. Полная очистка и повторная установка

Интерфейс предоставляет действие `Удалить созданные компоненты`. Перед запуском показывается явное предупреждение, что будут удалены данные и возможная инициализация управляемых ЛМ.

Удаление выполняется только при полном подтверждении ownership и в обратном порядке зависимостей:

1. остановить и удалить управляемые контроллеры выбранных ККТ;
2. удалить записи комплектов ККТ и пересчитать ссылки на каждый LM instance-id;
3. для ИНН, на чей ЛМ больше не ссылается ни одна ККТ, остановить API-, затем DB-службу и штатно завершить его EPMD;
4. удалить обе SCM-службы, повторно подтвердить их отсутствие и отсутствие принадлежащих им процессов/слушателей;
5. удалить app-owned конфигурацию, данные, key-store, журналы, operation journal и manifest освободившегося ИНН;
6. пересчитать ссылки на exact-version runtime по фактическим профилям, а не по доверенному счётчику из manifest;
7. только при нулевом числе ссылок, точном ownership и совпадении ожидаемых хэшей удалить общий runtime этой версии;
8. удалить созданные текущей операцией объекты ЕСМ только при наличии отдельного подтверждённого контракта и точного признака владения.

Частичное удаление одной ККТ не удаляет общий для других ККТ ЛМ. Действие «Удалить все созданные компоненты» завершает всю эту цепочку и после независимого обхода не оставляет ни app-owned профилей/служб, ни vendor-runtime, ни staging.

Если файл занят или служба помечена на удаление, строка получает `CleanupPending`. Повтор очистки доступен после перезагрузки без ручного поиска каталогов и SCM-записей.

Существующая штатная установка ЛМ, чужие каталоги и не подтверждённые manifest службы никогда не входят в пакетную очистку.

## 14. Обновление и совместимость версий

Встроенный автообновлятор присутствует только во временном административном образе, не копируется в общий управляемый runtime и не запускается. Управляемые экземпляры обновляются только через выбранный пользователем официальный MSI.

Для точной версии `2.6.1-7` поддерживаются установка, повторное обеспечение состояния и восстановление. Новый MSI сначала проходит новый capability gate. До подтверждения структуры и миграции данных существующие ЛМ остаются работоспособными, а действие обновления блокируется с состоянием `Проверка совместимости версии`.

Обновление не выполняется поверх работающего каталога и не проходит по строкам ККТ: единицей переключения является группа уникального ИНН. Новая версия извлекается в соседний versioned runtime и заранее проходит capability gate. Затем:

1. выбрать одну группу ИНН как upgrade-canary;
2. остановить все контроллеры ККТ, ссылающиеся на ЛМ этой группы, затем API- и DB-службы;
3. зафиксировать контрольную точку и создать защищённый снимок app-owned конфигурации и данных группы;
4. подготовить отдельные конфиги новой версии и, только при наличии проверенного адаптера точной пары версий, мигрировать данные;
5. атомарно переключить manifest и start plan обеих служб группы на новый exact-version runtime;
6. запустить DB, API и все контроллеры группы, проверить process ownership, слушатели, готовность ЛМ и привязки ККТ;
7. при ошибке вернуть только эту группу на предыдущие runtime, конфиги и данные, подтвердив восстановление;
8. после успешного canary последовательно переключить остальные группы ИНН;
9. удалить старый runtime только после независимого подтверждения нулевого числа ссылок на него.

Смешанное временное состояние, в котором разные группы ИНН используют разные точные версии, допустимо и отражается в manifest/UI. Автоматическая миграция между неизвестными схемами базы запрещена. Capability gate и VM-проверка выполняются для конкретной пары исходной и целевой версий; без них доступно только сохранение работающей версии или полное подтверждённое пересоздание пустого ЛМ.

## 15. Безопасность и граница независимой реализации

Архив `RollingPinForLM.1.3.1.Net4.8.zip` использовался только для подтверждения бизнес-сценария и высокоуровневого понимания, что старые версии ЛМ запускались несколькими экземплярами. Его код, PDB, конфигурационные шаблоны, названия классов, UI, тексты, команды и ресурсы не копируются. Хэши, происхождение и разрешённая граница исследования зафиксированы отдельно в `docs/research/2026-08-29-local-module-package-provenance.md`.

Реализация основывается на:

- свойствах официального MSI, полученных Windows Installer API;
- неизменённых файлах официального пакета;
- публичных Windows API;
- собственных моделях, именах, интерфейсе и алгоритмах проекта;
- воспроизводимых наблюдениях чистой VM.

Репозиторий остаётся private. В Git, CI и релизные ZIP запрещено добавлять:

- MSI ЛМ ЧЗ;
- извлечённые vendor-файлы;
- преобразованные пакеты;
- каталоги данных ЛМ;
- сертификаты, токены, cookies и учётные данные;
- сырые evidence-выгрузки с персональными путями.

Компактная сборка программы остаётся сборкой по умолчанию. Пользователь предоставляет оба официальных установщика самостоятельно.

## 16. Ошибки и наблюдаемость

Пользовательские сообщения формулируются по этапам и ККТ, например:

- `ККТ №2: MSI ЛМ не прошёл проверку подписи`;
- `ККТ №2: порт ЛМ 6995 занят процессом ...`;
- `ККТ №2: база ЛМ запущена, API ЛМ не открыл порт`;
- `ККТ №2: ЛМ готов к инициализации, контроллер не привязан к ЕСМ`.

Основной экран не показывает stack trace, SCM flags и внутренние исключения. Технические подробности попадают в защищённый журнал с маскированием путей пользователя и чувствительных полей.

Кнопка отмены прекращает только ещё не начатые строки. Уже созданная строка приводится в согласованную контрольную точку; принудительное убийство `msiexec`, базы или API без последующей сверки ownership запрещено.

## 17. Проверки и критерии приёмки

Функция готова к тестовой эксплуатации только если выполнены все условия:

1. Тесты планировщика подтверждают стабильные номера `K` и `N`, пары ЛМ `5995/5984`, `6995/6984`, `7995/7984`, gRPC `45001–45032` и отсутствие скрытого переназначения.
2. Две ККТ одного ИНН получают разные контроллеры, но один LM instance-id, один endpoint и одну пару служб; ККТ разных ИНН получают разные ЛМ.
3. Неизвестный, неподписанный, подменённый или структурно несовместимый MSI блокируется до изменений системы.
4. Официальный `2.6.1-7` извлекается фиксированным `/a /qn`, не показывает мастер и не создаёт штатные службы.
5. Два и более ЛМ одновременно используют один read-only runtime, отдельные app-owned конфиги/данные и независимые пары служб; попытка записи в runtime проваливается.
6. Все API-, DB- и отдельные EPMD-порты одновременно слушаются ожидаемыми процессными деревьями, идентифицированными также по parent PID, командной строке с точным config path и process-local окружению.
7. Остановка или удаление ЛМ одного ИНН не влияет на ЛМ других ИНН; удаление одной ККТ не удаляет ЛМ, пока на него ссылается другая ККТ того же ИНН.
8. После перезагрузки все оставленные экземпляры запускаются без входа пользователя и без запуска основной программы.
9. Состояние до бизнес-инициализации отображается как `Готов к инициализации`, а не как полностью рабочий ЛМ.
10. Повторный запуск не создаёт дубликаты и не меняет закреплённые номера и порты; legacy-профиль с явным `550xx` не перенумеровывается молча.
11. Ошибка первого full-chain canary не допускает регистрации или создания оставшихся строк; после успешного canary независимая ошибка одной последующей группы не блокирует уже безопасно выполняемые группы.
12. Пакетная очистка удаляет принадлежащие программе службы, профили, данные, журналы, manifest и staging; общий runtime удаляется только при нулевом числе фактических ссылок.
13. После перезагрузки повтор очистки завершает объекты `CleanupPending`, а повторная установка проходит без ручной чистки.
14. Существующие штатные `regime`/`yenisei` и чужие каталоги не изменяются даже при конфликте; конфликт показывается пользователю.
15. Автоматический сценарий обрабатывает одну и несколько ККТ одним подтверждением и одним пакетным UAC.
16. В основной таблице нет внутренних колонок служб и DB; видны только номер и данные ККТ, порт кассового ПО, endpoint ЛМ и два понятных состояния. Для общего ИНН endpoint повторяется честно.
17. Обновление exact-version runtime сначала проходит на одной группе ИНН, откатывает только её при ошибке и не удаляет старую версию до нулевого числа ссылок.
18. Реальные vendor-файлы отсутствуют в Git, тестовых фикстурах и компактном релизе.
19. Shared-тесты проходят в `net8.0` и `net48`, helper-тесты и обе WinForms-сборки проходят существующие CI- и safety-гейты.
20. В чистой VM отдельно подтверждены итоговые `vm.args`, `sys.config`, неизменность общего `erl.ini`, process-local `ERL_EPMD_PORT`, корректное завершение Erlang-процессов и отсутствие межэкземплярных конфликтов EPMD.
21. Сквозная проверка с реальной ККТ подтверждает цепочку `ККТ -> ЕСМ -> ЛМ -> контроллер`; создание самих ЛМ и служб допускается проверять без физической ККТ.
22. До первого изменения системы показана точная информация о лицензионной и эксплуатационной границе: ЛМ предоставляется безвозмездно, услуги установки/настройки в это предоставление не входят, число ЛМ определяется уникальными ИНН выбранной торговой точки.
23. После полной очистки в системе не остаётся ни app-owned профилей, ни принадлежащих программе служб, ни неиспользуемых копий vendor-runtime, ни извлечённого образа/staging; проверка выполняется независимым обходом SCM и файловой системы, а не только по manifest.

До выполнения VM-пунктов функция считается реализацией-кандидатом и не включается в публичный релиз.
