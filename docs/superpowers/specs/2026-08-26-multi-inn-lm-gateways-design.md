# Несколько контроллеров ЛМ ЧЗ для ККТ с разными ИНН

**Статус:** проект решения для ревью. Реализация, регистрация и удаление Windows-служб еще не выполнялись.

**Связанные планы:**

- `docs/superpowers/plans/2026-08-26-lm-gateway-esm-binding.md` — безопасный контракт ЕСМ, модели и управляющая логика;
- `docs/superpowers/plans/2026-08-26-lm-gateway-service-provisioning.md` — проверка совместимости контроллера, создание и удаление служб, итоговый интерфейс и поставка.

## 1. Задача

На одном компьютере работают несколько физических ККТ. Каждая ККТ зарегистрирована на свой ИНН и представлена отдельным экземпляром ЕСМ/ТС ПИоТ. Для каждой такой ККТ нужен отдельный экземпляр контроллера ЛМ ЧЗ со своими локальными портами и со своим адресом целевого ЛМ ЧЗ.

Пользователь должен выполнить обе части настройки в одном окне программы:

1. создать и зарегистрировать несколько ККТ в ЕСМ существующим ручным или автоматическим сценарием;
2. на новой вкладке создать для зарегистрированных ККТ контроллеры ЛМ ЧЗ, привязать к ним экземпляры ЕСМ, видеть состояние и удалять созданные программой службы.

Для каждой строки конфигурации связь выглядит так:

```text
ККТ / экземпляр ЕСМ
  (id = серийный номер ККТ, ИНН)
        |
        | PUT /api/v1/settings/lm/{id}
        v
локальный контроллер ЛМ ЧЗ
  (127.0.0.1:уникальный gRPC, уникальный REST)
        |
        v
целевой ЛМ ЧЗ
  (введенный пользователем адрес:порт)
```

## 2. Термины и идентичность

- **Экземпляр ЕСМ** — запись ККТ в `/api/v1/instances/info`; ее `id` должен совпадать с серийным номером ККТ.
- **Штатный контроллер** — единственная служба, созданная официальным установщиком контроллера ЛМ ЧЗ. В первой версии она отображается только для диагностики и не назначается ККТ.
- **Управляемый контроллер** — дополнительная Windows-служба, созданная этой утилитой из официально установленного и проверенного бинарного файла контроллера.
- **Локальные порты контроллера** — gRPC-порт, который передается ЕСМ, и отдельный REST-порт самого экземпляра контроллера.
- **Целевой ЛМ** — адрес и порт конкретного ЛМ ЧЗ, к которому должен обращаться контроллер.
- **Профиль контроллера** — отдельный каталог конфигурации управляемой службы. Профиль не содержит пароль, передаваемый ЕСМ.

Главный ключ — серийный номер ККТ / `id` экземпляра ЕСМ. ИНН является обязательным атрибутом и отображается пользователю, но не используется как имя службы и не заменяет идентификатор ККТ. Поэтому схема корректна и для двух ККТ одного ИНН, хотя исходный рабочий сценарий — разные ИНН.

## 3. Цели

- Показать зарегистрированные ККТ, их ИНН, существующие контроллеры и порты в одном месте.
- Детерминированно назначать каждой ККТ отдельные локальные gRPC/REST-порты без конфликтов.
- Предзаполнять адрес и порты детерминированно по порядковому номеру ККТ для обычной схемы на одном ПК, сохраняя возможность ручного изменения для нестандартной сети.
- Создавать отдельную управляемую службу для каждой выбранной ККТ только из официально установленного контроллера и только после проверки совместимости его конкретной версии.
- Выполнять привязку ЕСМ документированным запросом `PUT /api/v1/settings/lm/{id}`.
- Продолжать обработку остальных ККТ после локальной ошибки одной строки.
- Поддерживать повторный запуск без создания дубликатов.
- Дать пользователю возможность остановить и удалить управляемую службу из интерфейса.
- Не записывать пароль ЛМ ни в журнал, ни в профиль службы, ни в диагностический текст, ни в долговременное состояние программы.
- Сохранить компактную поставку по умолчанию; самодостаточные Modern-сборки примерно по 60 МБ не публиковать без отдельного запроса.

## 4. Не входит в объем

- Установка, обновление или распространение бинарных файлов ЛМ ЧЗ и контроллера ЛМ ЧЗ.
- Изменение, патчинг, упаковка, распаковка или внедрение данных в бинарный файл контроллера.
- Клонирование сертификатов, ключей, токенов или всего каталога данных штатной службы.
- Создание junction/symlink/reparse point, изменение machine-wide/SCM environment или передача произвольного environment из UI/IPC. Единственное исключение — зафиксированный capability profile: app-owned supervisor задаёт отдельный `ProgramData` только дочернему процессу контроллера.
- Обход ограничений официального установщика или лицензионных проверок.
- Автоматическая установка сетевых правил брандмауэра: локальные слушатели должны оставаться на loopback, если версия контроллера это поддерживает.
- Назначение, перенастройка или автоматическое удаление штатной службы: она остается диагностической и обслуживается официальными средствами.
- Гарантированное криптографическое стирание секторов диска. При удалении обычные файлы профиля и метаданные удаляются средствами ОС после строгой проверки пути.
- Автоматическая «отвязка» ЕСМ при удалении службы, пока для этого не найден и не подтвержден официальный контракт.
- Скрытое создание служб без явного запуска пользователем. Кнопка полного автоматического режима является подтверждением всего последовательного сценария; повышение прав запрашивается ОС только когда оно действительно требуется текущему токену.
- Изменение существующего распределителя ЕСМ-портов `504xx/514xx`: это отдельный жизненный цикл, не часть LM Gateway-планов и не причина смешивать его с `LmGatewayPlanner`.

Отдельный P1 backlog перед следующим функциональным релизом: для manual и bulk регистрации ККТ перед планированием получать через внедряемую абстракцию снимок реально слушаемых TCP-портов, пропускать занятую пару `504xx/514xx` и повторно проверять выбранную пару непосредственно перед первым изменяющим запросом. Реализация не должна вызывать `netstat`/shell или переносить Windows API в чистый `KktPortPairAllocator`; TOCTOU полностью не устраняется, поэтому существующая обработка отказа ЕСМ и recovery-сценарий сохраняются. Backlog оформляется отдельным TDD-планом и не меняет счетчики тестов двух текущих LM-планов.

## 5. Источники и граница независимой реализации

Подтвержденный внешний контракт:

- официальная инструкция CSI показывает `PUT /api/v1/settings/lm/{id}` с JSON-полями `address`, `port`, `login`, `password`;
- в этой схеме `address` и `port` — адрес компьютера с контроллером и gRPC-порт контроллера, а не REST-порт целевого ЛМ ЧЗ;
- официальная инструкция указывает, что Windows-контроллер ставится интерактивным установщиком, но не документирует несколько служб, отдельный путь конфигурации, параметры командной строки или удаление LM-настройки из ЕСМ.

Источники:

- https://crystals.atlassian.net/wiki/spaces/SR10SUPPORT/pages/6404898850/SetRetail10
- https://markirovka.ru/knowledge/tovarnye-gruppy/obschie-voprosy-gis/chto-takoe-po-lokalnyy-modul-chestnyy-znak-%29

Архив стороннего ПО `RollingPinForESM.zip` уже исследовался статически для оценки реализуемости, поэтому называть дальнейшую работу строгой юридической clean-room-разработкой было бы неточно. Для снижения риска дальнейшая реализация должна опираться только на:

1. официальные публичные инструкции;
2. собственные наблюдения за официальным установщиком и официальной службой в одноразовой виртуальной машине;
3. публичные Windows API;
4. самостоятельно спроектированные модели, имена, интерфейс, тексты и сценарии.

В код, ресурсы и документацию запрещено переносить из стороннего ПО:

- исходный или декомпилированный код;
- имена его классов, функций, внутренних сущностей и файлов;
- тексты интерфейса, макеты, иконки и другие ресурсы;
- готовые PowerShell/Batch-сценарии;
- приемы патчинга бинарников, UPX, junction-подмены и принудительного завершения процессов.

Официальные названия компонентов, URL API, имена JSON-полей, номера портов и прочие необходимые факты совместимости используются как внешний протокол. Для внутренних сущностей проекта применяется собственная терминология `LmGateway*`; в русском интерфейсе остается понятное официальное название «Контроллер ЛМ ЧЗ».

Перед реализацией создается журнал происхождения технических фактов. Репозиторий и рабочая ветка остаются private; артефакты всё равно разделяются по минимуму необходимых данных:

- в private Git попадает только compatibility summary: версия/хэш/подписант официального бинарника, высокоуровневые инварианты, итоги обоих gate, идентификаторы и SHA-256 локальных evidence items, методика без raw output;
- полные SCM/filesystem/registry diffs, абсолютные пути, SDDL/DACL, service account/dependencies/recovery, process tree, raw `--help`, внутренние field paths/schema и снимки VM остаются в локальном access-controlled evidence pack вне рабочего дерева;
- каждый локальный evidence item получает `EvidenceId`, описание источника/команды, очищенный raw result и SHA-256; summary содержит только идентификатор, digest и вывод.

`TechnicalCompatibilityGate` и `PublicationGate` не подменяют друг друга. Black-box-наблюдение может обосновать частную версионную реализацию, но не разрешает её автоматическую публикацию. Любой vendor-specific путь, switch, schema discriminator или field name может попасть в public source/build только при наличии официальной публичной документации либо явного разрешения правообладателя.

## 6. Пользовательский интерфейс

В главное окно добавляется самостоятельная вкладка `Контроллеры ЛМ ЧЗ` между `Автоматический режим` и `Журнал`. Логику вкладки следует вынести из уже крупного `MainForm` в отдельный `LmGatewayPage : UserControl`.

Над таблицей находится поле выбора `esm-lm-controller_*-windows-setup.exe`. Файл выбирается через стандартный диалог, не запускается при выборе и используется только после показа version, signer и SHA-256. Полный путь хранится только в текущей UI-сессии и не попадает в settings, manifest или журнал.

### 6.1. Таблица

Над таблицей отдельный информационный блок показывает наличие, имя и состояние штатной службы официального установщика. Штатная служба не является строкой ККТ и не смешивается с выбираемыми управляемыми экземплярами.

Таблица показывает:

- выбор строки;
- серийный номер ККТ;
- ИНН;
- состояние экземпляра ЕСМ;
- роль контроллера: `Управляемый`, `Не создан` или `Неизвестный`;
- имя Windows-службы;
- локальный gRPC-порт;
- локальный REST-порт;
- адрес и порт целевого ЛМ;
- состояние службы;
- состояние привязки ЕСМ;
- последнее действие / ошибка.

Пароль в таблице не отображается. Логин можно показывать только в текущей сессии; в долговременное состояние он не записывается вместе с паролем.

### 6.2. Редактор выбранной строки

Под таблицей находятся поля:

- `Адрес ЛМ ЧЗ`;
- `Порт ЛМ ЧЗ`;
- `Логин ЛМ ЧЗ`;
- `Пароль ЛМ ЧЗ` с маскированным вводом;
- `gRPC-порт контроллера`;
- `REST-порт контроллера`.

Обычная схема предполагает работу на одном ПК и предзаполняется по стабильному порядковому номеру ККТ после сортировки по серийному номеру: №1 получает целевой ЛМ `127.0.0.1:5995`, gRPC `45001`, REST `15001`; №2 — `127.0.0.1:6995`, `45002`, `15002`; №3 — `127.0.0.1:7995`, `45003`, `15003` и далее в той же последовательности. Номер ККТ виден отдельной колонкой и совпадает с окончанием локальных портов. Пользователь изменяет значения только для нестандартной сети. Явно занятый порт блокирует строку и не вызывает бесшумного сдвига номера. Ранее сохранённые управляемые профили с явными портами `55001–55032` считаются legacy-настройками: они повторно проверяются и сохраняются без скрытого переназначения либо пересоздаются только после отдельного подтверждения пользователя.

Адрес/порт целевого ЛМ и явный выбор локальных портов сохраняются в профиле текущего пользователя. Черновик восстанавливается только при точном совпадении серийного номера ККТ и ИНН. Логин и пароль не входят в долговременный формат и после закрытия программы теряются.

### 6.3. Действия

- `Обновить` — заново получить ККТ из ЕСМ и прочитать состояние служб без изменений системы.
- `Выбрать…` — выбрать официальный installer и выполнить без повышения прав предварительную проверку.
- `Установить и настроить ККТ` — повторно проверить и установить выбранную версию, построить план по текущим строкам, создать/обновить службы, проверить их и выполнить доступные привязки к ЕСМ одним явным действием.
- `Настроить всё автоматически` на вкладке автоматического режима — если установщик ещё не выбран, сразу открыть его выбор; затем последовательно выполнить регистрацию ККТ и тот же единый сценарий установки и настройки контроллеров без второго диалога и второго нажатия.
- `Остановить` — передать отмену текущему этапу; остановка происходит на поддерживаемой им безопасной границе, завершённые действия не откатываются.
- `Повторить привязку к ЕСМ` — не пересоздавать службу, а повторить только безопасный PUT для готовой строки.
- `Удалить службу` — доступно только для управляемой службы с подтвержденной меткой владения.
- `Удалить все созданные` — аварийное восстановление после неудачной настройки: одним helper/UAC удалить все заново подтверждённые управляемые службы и их локальные данные, не затрагивая штатную службу и привязки ЕСМ.

После запуска полного автоматического режима программа сама переходит от массовой регистрации к созданию контроллеров. Повторная реализация service-provisioning в `MainForm` запрещена: автоматический режим вызывает тот же координатор вкладки контроллеров. Если регистрация отменена или не подготовлена, этап контроллеров не запускается.

### 6.4. Подтверждение и итог создания

Явное нажатие `Установить и настроить ККТ` или `Настроить всё автоматически` подтверждает последовательную операцию. Предварительный модальный план не нужен: все вычисленные значения заранее видны в таблице, а невалидные или занятые порты блокируют мутацию до запуска helper. Для каждой ККТ в таблице и итоге видны:

- ККТ и ИНН;
- создать, оставить без изменений или перенастроить службу;
- имя службы;
- локальные порты;
- целевой ЛМ;
- последующая привязка ЕСМ;
- ошибки и предупреждения.

Пароль вообще не входит в план; показывается только `credentials заданы/не заданы`. Строка с ошибкой не исполняется, но не блокирует запуск остальных выбранных корректных строк.

### 6.5. Подтверждение удаления

Диалог удаления показывает ККТ, ИНН, точное имя службы, локальные порты и предупреждение о том, что:

- служба будет остановлена и удалена;
- профиль, manifest и созданные программой локальные метаданные будут удалены без возможности восстановления средствами программы;
- настройки связи в ЕСМ могут продолжать ссылаться на удаленный контроллер;
- штатная служба официального установщика этим действием не удаляется.

Для пакетной аварийной очистки отдельный диалог показывает полный отсортированный список управляемых служб и требует точную фразу `УДАЛИТЬ ВСЕ`. После подтверждения UI перечитывает inventory и отклоняет весь запрос при изменении состава, fingerprint или портов. Helper повторно проверяет владение каждой строкой и обрабатывает их последовательно в одном запуске; ошибка одной строки не разрешает мутацию этой строки и не скрывает результаты остальных.

Для подтверждения пользователь вводит серийный номер ККТ. Простого нажатия `Да` недостаточно.

## 7. Распределение портов

Штатная установка часто использует gRPC `50063` и REST `5063`, но эти значения считаются только наблюдаемыми портами штатной службы. Они не являются началом пула управляемых экземпляров.

Штатная служба и ее фактические порты отображаются отдельно и никогда не назначаются ККТ автоматически. Каждая выбранная ККТ получает собственную управляемую службу. Это исключает риск бесшумно связать ККТ одного ИНН с уже настроенным штатным контроллером другого ИНН.

Управляемые порты не начинаются с `50063+n`: `50063` входит в стандартный динамический TCP-диапазон современных Windows. Compatibility profile фиксирует конечные разрешённые пулы `45001–45032` для gRPC и `15001–15032` для REST, проверенные на поддерживаемых ОС. Планировщик сохраняет соответствие порядковому номеру ККТ и не сдвигает строку на первый свободный порт молча; окончательное право использовать выбранную пару подтверждает привилегированный помощник непосредственно перед запуском службы.

Планировщик обязан учитывать:

- все уже управляемые профили;
- фактически занятые TCP-порты;
- порты штатной службы как занятые, но не переиспользуемые;
- порты в текущем еще не выполненном плане;
- конфликт gRPC и REST между любыми двумя строками;
- конфликт с целевым ЛМ, если его адрес loopback и номер порта совпадает с локальным слушателем.

Пользователь может выбрать порт только внутри соответствующего capability-approved пула. Невалидная строка не резервирует порты для следующих строк. План строится детерминированно по серийному номеру ККТ, чтобы повторное открытие не перемешивало назначения.

Перед изменением профиля/SCM helper повторяет проверку фактических слушателей и временно занимает оба порта сокетами с `ExclusiveAddressUse=true` и без `ReuseAddress` на точном наборе IPv4/IPv6 endpoint из compatibility profile. Profile отдельно фиксирует loopback/wildcard и IPv6-only/dual-stack семантику контроллера. Ошибка `bind` (в том числе из-за занятого или исключенного системой порта) блокирует только эту ККТ. Сокеты освобождаются непосредственно перед стартом службы; если порт успевает занять другой процесс, запуск честно завершается конкурентной ошибкой готовности, чужой процесс не завершается и профиль не привязывается к ЕСМ.

## 8. Архитектура

### 8.1. Общая библиотека

`EsmTspiot.Shared` содержит только платформенно-независимые модели и чистую управляющую логику:

- `LmGatewayDiscoveryWorkflow` — получает зарегистрированные ККТ и полные регистрационные данные;
- `LmGatewayPlanner` — сопоставляет ККТ, профили, порты и введенные параметры;
- `LmGatewayBindingWorkflow` — выполняет только привязку готового локального контроллера к ЕСМ;
- `LmGatewayLifecycleWorkflow` — координирует создание/проверку/привязку и удаление через абстракции;
- `ILmServiceProvisioner` — граница привилегированного помощника;
- `ILmGatewayProbe` — проверка состояния слушателей и владения процессом;
- типизированные DTO без WinForms и без прямого доступа к SCM.

Существующий `BulkRegistrationWorkflow`, `KktPortPairAllocator` и `ServiceRecoveryCommandBuilder` не расширяются логикой контроллера ЛМ: это другие жизненные циклы и другие диапазоны портов.

### 8.2. Привилегированный помощник

Создание, изменение и удаление службы выполняет отдельный небольшой `net48`-процесс `EsmTspiot.ServiceProvisioner.exe`, запускаемый через UAC только на изменяющие действия.

Причины отдельного процесса:

- основное окно остается без постоянных прав администратора;
- SCM-операции имеют узкий типизированный контракт;
- в коде нет строково собранного `sc.exe` или PowerShell;
- проверку и транзакцию можно тестировать отдельно от WinForms.

Один запуск помощника принимает один ограниченный пакет `EnsureBatch` (не более 32 ККТ), одно удаление `RemoveManaged`, пакет подтверждённых удалений `RemoveAllManaged` (не более 32 ККТ) либо повтор `CleanupManaged`. Запрос передается по одноразовому named pipe с 128-битным случайным идентификатором, initiating SID и SHA-256 от показанного пользователю канонического плана/подтверждения. UI и helper сверяют `operationId`, SID, peer PID/image и hash. Helper повторно валидирует каждый элемент; ошибка одного элемента не дает ему изменить этот элемент, но не отменяет остальные корректные элементы.

Обе стороны проверяют не только SID. UI принимает соединение только от PID запущенного helper с точным защищенным путем и встроенным в основной EXE хэшем. Helper принимает pipe server только от точного основного EXE этого выпуска из родительского защищенного каталога, с ожидаемыми product/company/version. Несовпадение проверяется до чтения рабочего payload и исключает использование helper как privileged confused deputy процессом того же пользователя.

Named pipe доступен только initiating SID, `SYSTEM` и `Administrators`. Первая версия поддерживает повышение split-token того же локального администратора; ввод учетных данных другого администратора из стандартной учетной записи не поддерживается. Это ограничение показывается до UAC. После запуска helper UI не начинает новую мутацию до reconciliation того же `operationId`.

Все опасные значения вычисляются заново и проверяются внутри помощника. Пользователь не задает имя службы, путь к бинарному файлу, учетную запись службы, аргументы запуска, переменные окружения или каталог профиля. Помощник использует Windows SCM API через P/Invoke. Shell-команды и запись per-service environment не используются.

### 8.3. Управляемое состояние

Метаданные и рабочий профиль физически разделены:

```text
%ProgramData%\KRS\MultiKKT\Inventory\<service-name>\manifest.json
%ProgramData%\KRS\MultiKKT\Profiles\<service-name>\...
```

Inventory-manifest содержит:

- версию схемы;
- серийный номер ККТ;
- имя службы;
- локальные gRPC/REST-порты;
- адрес и порт целевого ЛМ;
- путь и хэш официального бинарного файла;
- версию контроллера;
- последнее подтвержденное локальное состояние, `operationId`, безопасный класс последней ошибки очистки и время изменения.

Inventory-manifest не содержит логин, пароль, токен, API-ключ или содержимое профиля. Запись выполняется атомарно через временный файл и replace. Чтение получает только initiating SID, зафиксированный при создании, а `SYSTEM` и `Administrators` имеют полный доступ. `BUILTIN\Users` и `Authenticated Users` доступа не получают.

Профиль может содержать секреты, созданные самим официальным контроллером, поэтому UI никогда его не читает. DACL профиля дает необходимые права только `SYSTEM`, `Administrators` и фактической service identity конкретной службы; другие управляемые службы не получают доступ к чужому профилю. Если контроллер требует общую `LocalSystem` identity и не позволяет изолировать профили, compatibility gate завершается FAIL.

Reparse points запрещены во всех production-путях. До первой SCM-мутации helper атомарно пишет operation journal в состоянии `Preparing`; перед изменением/удалением — `Updating`/`Deleting`. Перед запуском выбранного установщика все управляемые строки атомарно переводятся в `VersionVerificationPending`; для точного capability-профиля `1.6.3.2` защищённая staging-копия запускается с фиксированным NSIS-ключом `/S`, а произвольные аргументы из UI/IPC запрещены. `Ready` возвращается только после явного `Ensure` и проверки listeners. `Ready` и `Removed` записываются только после фактической проверки. Machine-wide mutex и отдельный per-KKT mutex исключают параллельные `Install/Ensure/Remove/Cleanup`. При старте helper сначала reconciles незавершенные операции.

Для удаления одного совпадения имени недостаточно. Помощник требует одновременно:

1. допустимый префикс собственного имени службы;
2. валидный app-owned manifest;
3. совпадение имени службы, ККТ и профиля;
4. совпадение канонического ImagePath и идентичности исполняемого файла с exact-version execution contract из capability profile;
5. собственную типизированную метку в описании службы.

При несовпадении хотя бы одного признака строка получает статус `Неизвестная служба`; изменение и удаление блокируются.

Точная поддерживаемая версия/хэш обязательны для создания и запуска, но не превращаются в ловушку удаления. Если официальный EXE позже обновлен или удален, уже управляемую службу разрешено остановить и убрать после совпадения manifest, метки, производного имени и сохраненного exact-version execution descriptor внутри защищённых roots: удаление бинарник не запускает и сам официальный файл не удаляет.

## 9. Проверка совместимости официального контроллера

Многослужебный режим нельзя реализовывать по предположению. Для private-ветки сначала выполняется `TechnicalCompatibilityGate` на конкретной версии официального установщика. Перед любым переводом в public отдельно выполняется `PublicationGate` для всех vendor-specific фактов в source, tests, docs и compiled builds. Неуспех публикационной проверки не отменяет технический вывод, но сохраняет код и сборки частными.

Для версии `1.6.3.2` техническая характеризация завершена 2026-08-27 со статусом `TechnicalCompatibilityReady`. Два чистых прогона подтвердили одинаковое поведение, третий контроль подтвердил самостоятельную генерацию ключей и сертификатов в пустом профиле. `PublicationGate` остаётся `PublicSourcePending`, поэтому service-provisioning код и сборки остаются private.

Необходимо независимо подтвердить для конкретной версии:

- подписанта, версию, хэш и фактический путь бинарного файла;
- ImagePath, start type, service account, dependencies и recovery-настройки штатной службы;
- какие каталоги и реестровые ключи создаются при первом запуске;
- какой из режимов даёт отдельный config/data path: официальный параметр, non-reparse execution path/hard link или app-owned supervisor;
- где и в каком типизированном формате задаются локальные gRPC/REST-порты и целевой LM endpoint, и что контроллер не требует дополнительного секрета в своем профиле помимо credentials, передаваемых ЕСМ через документированный PUT;
- можно ли изменить конфигурацию атомарно при остановленной службе;
- какие слушатели создает служба и принадлежат ли они ожидаемому подписанному процессу;
- отсутствует ли общая machine-wide запись, из-за которой второй экземпляр портит первый.

Поддержка конкретной версии оформляется как проверенный capability profile. Проверка изоляции идёт в порядке: официальный data/config switch, отдельный путь без reparse point/hard link, app-owned supervisor. Junction разрешён только как контрольный VM-опыт и не переносится в production без отдельного threat model и повторного архитектурного ревью. Патчинг бинарника, UPX, перенос секретов и копирование всего штатного профиля запрещены. Если ни один безопасный способ не даёт независимые профили/порты, gate завершается `TechnicalCompatibilityRejected`.

Для `1.6.3.2` capability profile выбирает только app-owned supervisor. Самодокументируемый CLI не содержит data/config switch; отдельный execution path сам по себе профиль не изолирует. Супервизор запускает точный проверенный бинарный файл в terminal mode, формирует его environment block из безопасного базового окружения и заменяет только `ProgramData` на строго производный app-owned root конкретной службы. `ALLUSERSPROFILE`, machine-wide environment и SCM-registry environment не изменяются. UI/IPC не передают имя environment key, путь или vendor arguments.

Каждая служба супервизора получает `SERVICE_SID_TYPE_RESTRICTED`. Профиль допускает администраторов/SYSTEM для управления и SID только своей службы для runtime-доступа; restricted token дочернего процесса обязан блокировать чтение чужого профиля. В новый профиль записывается только минимальная конфигурация без ключей/сертификатов. Официальный контроллер сам создаёт новый CA/server key material при первом запуске; копирование штатного профиля или любого PEM запрещено.

## 10. Создание и обновление службы

Для каждой корректной строки выполняется:

1. повторная проверка официального бинарного файла, подписи, версии и хэша;
2. проверка всех портов непосредственно перед изменением;
3. создание operation journal и получение machine-wide/per-KKT mutex;
4. расчет собственного имени службы из строго проверенного 14-значного серийного номера;
5. создание пустого отдельного профиля без копирования секретов, сертификатов или ключей штатной службы;
6. атомарная запись минимальной конфигурации, подтвержденной capability profile;
7. создание или сверка app-owned supervisor-службы с restricted service SID;
8. запуск супервизора, который задаёт дочернему контроллеру только производный process-local `ProgramData`, и ожидание ожидаемых локальных слушателей;
9. подтверждение, что слушатели принадлежат точному проверенному дочернему процессу с ожидаемым parent PID;
10. только после готовности — `PUT /api/v1/settings/lm/{id}` с `address=127.0.0.1` и локальным gRPC-портом;
11. фиксация отдельного результата этапа службы и этапа ЕСМ.

Повторный запуск:

- полностью совпадающая и готовая служба не пересоздается;
- остановленная совпадающая служба запускается;
- собственная служба с отличающейся конфигурацией останавливается, получает атомарное обновление и запускается;
- чужая или неоднозначная служба не изменяется;
- готовая служба с неуспешным PUT остается работающей со статусом `Готова, не привязана`, чтобы пользователь мог повторить только привязку.

Если новая служба создана, но не вышла в готовность, она останавливается и сохраняется для диагностики; автоматического удаления и потери профиля нет.

## 11. Удаление службы

Обычная команда удаляет одну выбранную управляемую службу. Для восстановления после неудачной автоматической настройки разрешена отдельная пакетная команда `RemoveAllManaged`: она принимает только заранее показанный и повторно проверенный список управляемых служб, выполняется одним helper/UAC и никогда не включает штатную либо неизвестную службу.

Последовательность:

1. повторно проверить все признаки владения;
2. проверить фактическое имя, ImagePath и PID;
3. остановить службу штатным SCM-запросом;
4. дождаться состояния `Stopped` с ограниченным таймаутом;
5. вызвать `DeleteService`, закрыть все собственные handles к службе и учесть состояние `MarkedForDelete`;
6. подтвердить отсутствие только когда bounded poll завершился `OpenService == ERROR_SERVICE_DOES_NOT_EXIST`;
7. записать в operation journal состояние `Cleaning` и атомарно опубликовать в остающемся inventory-manifest безопасную проекцию `CleanupPending`;
8. заново канонизировать строго производные profile/manifest paths, проверить app-owned root и отсутствие reparse points;
9. удалить профиль и иные локальные метаданные, явно перечисленные в capability profile, подтвердить их отсутствие и только затем удалить manifest;
10. удалить operation journal последним и обновить строку интерфейса/журнал.

Если service PID, разрешенный child PID или listener PID еще живы после `SERVICE_STOPPED`, конфигурация и профиль не меняются, а удаление не считается завершенным. `MarkedForDelete`, timeout и access denied дают разные результаты. Принудительный `taskkill` не применяется.

Рекурсивная очистка выполняется только после подтвержденного отсутствия службы и процессов, по заново проверенному абсолютному пути строго внутри `%ProgramData%\KRS\MultiKKT\Profiles`. Если хотя бы один файл не удален, manifest остается со статусом `CleanupPending`; после перезапуска UI снова показывает точную управляемую строку и кнопку `Повторить очистку`, которая выполняет все проверки заново. Даже если процесс оборвался до обновления статуса, сочетание валидного manifest и отсутствующей SCM-службы классифицируется как `CleanupPending`. Пользователю не предлагается искать или удалять каталог вручную.

Документированного API очистки `/settings/lm/{id}` не найдено. Поэтому после локальной очистки ЕСМ может продолжать хранить старый адрес и порт. Интерфейс обязан показывать `Служба и локальные данные удалены; привязка ЕСМ сохранена` и предлагать создать службу заново либо привязать ККТ к другому готовому контроллеру. Нельзя писать пользователю «настройка полностью удалена».

Штатная служба отображается, но кнопка удаления для нее недоступна. Рядом показывается подсказка об использовании официального деинсталлятора.

Inventory читается при открытии страницы независимо от доступности ЕСМ. Поэтому после перезагрузки сохранённые защищённые manifest/journal снова показывают управляемые или `CleanupPending` строки и позволяют повторить пакетное удаление/очистку без ручного поиска каталогов.

## 12. Секреты и журналирование

- Поле пароля использует `UseSystemPasswordChar`.
- Пароль живет только в памяти формы на время текущей операции.
- Пароль не попадает в DTO привилегированного помощника.
- `TspiotApiClient` отправляет реальное тело запроса, но сохраняет в `ApiResponse.RequestBody` только заранее маскированное тело.
- `LogFormatter` повторно маскирует чувствительные JSON/key-value поля до записи и в UI, и в файл.
- Ответы сервера и тексты исключений также проходят маскирование: сервер может отразить запрос.
- `DiagnosticMasker` остается вторым уровнем защиты для копирования диагностики.
- План подтверждения, итоговые результаты и manifest вообще не содержат поле пароля; в UI вместо введенного значения показывается только факт `задан`.
- После завершения или отмены UI удаляет ссылки на короткоживущие credential-объекты. Документация не обещает надежное обнуление immutable-строк .NET.

## 13. Состояния и восстановление

Отдельно фиксируются состояния службы и ЕСМ. Минимальные итоговые статусы:

- `Planned`;
- `Preparing`;
- `Updating`;
- `VersionVerificationPending`;
- `Deleting`;
- `Invalid`;
- `Unchanged`;
- `ServiceCreated`;
- `ServiceUpdated`;
- `ServiceReady`;
- `ServiceFailed`;
- `BindingAccepted`;
- `BindingObserved`;
- `BindingVerified`;
- `BindingFailed`;
- `ReadyNotBound`;
- `Cancelled`;
- `RemovalBlocked`;
- `MarkedForDelete`;
- `RemovedLocalArtifactsBindingRetained`;
- `CleanupPending`;
- `RequiresAttention`.

`BindingVerified` выставляется только после успешного `GET /api/v2/info`, когда серийный номер ККТ, ИНН и сообщаемый ЕСМ endpoint целевого ЛМ ЧЗ (`lm.ip`/`lm.port`) совпали с ожидаемыми. Если endpoint виден, но локально нет ожидаемой пары для сверки, используется `BindingObserved`, а не ложное подтверждение. Это не gRPC/REST-порты локальной службы контроллера: смешивать `5995/6995/...` с `45001/45002/...` запрещено. Сам по себе ответ 2xx на PUT остаётся `BindingAccepted`. При обновлении страницы тот же read-back показывает уже существующую привязку; недоступность read-back не запускает повторный PUT.

До запуска helper отмена прекращает весь пакет. После аутентификации helper UI отправляет `CancelAfterCurrentItem`: текущая атомарная операция завершается и reconciles, оставшиеся строки получают `Cancelled`. Потеря pipe трактуется так же, а не как разрешение создать все оставшиеся службы. Уже завершенные операции не откатываются. Если фактический результат SCM или HTTP-запроса неизвестен, программа не угадывает и не выполняет разрушительный rollback; она повторно читает состояние и ставит `RequiresAttention`.

## 14. Совместимость и поставка

- Общая логика остается совместимой с `net48` и `net8.0` и с текущим C# 5-совместимым стилем системного компилятора.
- Legacy и Modern WinForms используют один UI-код.
- Привилегированный помощник — небольшой `net48` EXE без сторонних пакетов; создание/удаление доступно только из доверенного, не доступного на запись обычному пользователю каталога установки. В portable/user-writable запуске остаются доступны чтение и binding-only, а elevation отключена.
- Компактная поставка публикуется ZIP-архивом с Legacy EXE и его `EsmTspiot.Shared.dll` в корне, а helper и его отдельной net48-копией `EsmTspiot.Shared.dll` — в фиксированном подкаталоге `Provisioner`. Все файлы имеют контрольные суммы; разнесение исключает конфликт net8/net48 DLL при Modern publish.
- Modern self-contained x86/x64 не публикуются по умолчанию и собираются только по отдельному запросу.
- Если помощник отсутствует или не прошел проверку версии/целостности, чтение и привязка готового контроллера остаются доступны, а создание и удаление служб отключаются с понятным сообщением.

## 15. Критерии приемки

Функция готова к релизу только если:

1. Вкладка показывает все зарегистрированные ККТ и их ИНН, включая разные ИНН на одном ПК.
2. Для трех и более ККТ строятся уникальные локальные пары из проверенных пулов, и каждый порт проходит финальную эксклюзивную bind-проверку.
3. Адрес и порты каждой ККТ предзаполнены по её видимому порядковому номеру и допускают ручное изменение.
4. Для одной строки ошибка не останавливает корректные остальные строки.
5. Повторный запуск не создает вторую службу для той же ККТ.
6. PUT выполняется только после подтвержденной готовности локального контроллера.
7. Пароль отсутствует в UI-журнале, файловом журнале, диагностике, manifest и запросе помощника; поля `pass`/`token` из `/api/v2/info` маскируются до журналирования и не входят в read-back-модель.
8. Удаляется только управляемая служба с полным совпадением признаков владения.
9. После удаления служба, профиль, manifest и app-owned метаданные очищены программой; при занятом файле UI предлагает автоматический повтор, а сохраненная привязка ЕСМ показана отдельно.
10. Штатная служба только отображается: она не назначается ККТ, не перенастраивается и не удаляется.
11. Никакие junction, shell-скрипты, патчинг, копирование стороннего кода/ключей или machine-wide/SCM environment не используются; единственный `ProgramData` override создаётся супервизором в environment block своего дочернего процесса.
12. Тесты проходят в `net8.0` и `net48`, обе WinForms-сборки и помощник собираются в CI.
13. На одноразовой VM успешно воспроизводятся две supervisor-службы с restricted SID, независимые process-local `ProgramData`, порты/профили, самостоятельно созданные ключи, привязка трех ККТ, graceful stop, повторный запуск и удаление одной управляемой службы без влияния на остальные.
14. Private compatibility summary содержит источник API, ограничения удаления, версию/хэш установщика и раздельные статусы technical/publication gate.
15. Выбранный installer повторно проверяется и запускается из защищённой staging-копии; подмена между UI-проверкой и UAC блокируется.
16. После смены версии все прежние управляемые строки остаются остановленными в `VersionVerificationPending` до явного повторного `Ensure`; удаление и очистка при этом доступны.
17. Один запуск автоматического режима последовательно выполняет регистрацию ККТ, установку/проверку версии контроллера, создание служб и доступные привязки без второго подтверждения; неуспех регистрации не запускает этап контроллеров.
18. Если установщик не выбран, старт автоматического режима открывает проводник; поддерживаемый NSIS-пакет устанавливается с фиксированным `/S`. До релиза в чистой VM подтверждены точная командная строка, код выхода 0 и отсутствие мастера или интерактивных запросов.
19. После перезагрузки все оставленные управляемые службы автоматически возвращаются в готовое состояние без входа пользователя и запуска приложения.
20. После этой перезагрузки пакетная команда удаления одним helper/UAC очищает все заново подтверждённые управляемые службы, профили, manifest и app-owned журналы, но не штатную службу и не привязки ЕСМ; повторная перезагрузка не восстанавливает удалённые артефакты, а автоматическая установка снова проходит без ручной очистки SCM или каталогов.
