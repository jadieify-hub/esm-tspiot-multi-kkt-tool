# Независимые ЛМ ЧЗ через проверенные MSI-клоны

**Статус:** согласовано как целевая архитектура; реализация и стендовая приёмка ещё не выполнены.

**Целевая версия ЛМ ЧЗ:** `regime-2.6.1-7.msi`, ProductVersion `2.6.1`.

**Базовая ревизия проекта:** `b3511bc` — регистрация ККТ и прямые контроллеры остаются действующей основой.

Эта спецификация заменяет активную архитектуру управляемых ЛМ из
`2026-08-29-managed-local-module-instances-design.md`. Старые KRS-службы-supervisor,
общий runtime и постоянные процессы `EsmTspiot.ServiceProvisioner.exe` больше не являются
целевой схемой. Код распознавания и безопасной уборки подтверждённых legacy-остатков может
сохраниться только как миграционный механизм.

## 1. Цель и границы

Полная автоматическая настройка должна последовательно:

1. обнаружить физические ККТ через уже работающий последовательный VCOM-сценарий;
2. зарегистрировать или проверить экземпляры ККТ в ЕСМ;
3. создать для каждой ККТ независимый прямой контроллер ЛМ;
4. обеспечить один ЛМ ЧЗ на уникальный ИНН выбранной торговой точки;
5. привязать нужный endpoint ЛМ к экземпляру ЕСМ;
6. продолжить обработку остальных ККТ независимо от бизнес-инициализации ЛМ.

Инициализация ЛМ не является блокирующим этапом. Успешный технический итог до неё —
`ЛМ установлен и запущен; инициализация выполняется отдельно или автоматически ЕСМ`.

Несколько ККТ одного ИНН используют один ЛМ, но каждая ККТ имеет свой контроллер.
ККТ разных ИНН получают разные экземпляры ЛМ.

В поставку программы не входят исходный MSI ЛМ, перепакованный MSI, файлы установленного
ЛМ, cookies, пароли, сертификаты экземпляров или данные баз.

## 2. Выбранная модель установки

Первый экземпляр — обычная официальная установка:

| Роль | Каталог | Службы | API | CouchDB |
| --- | --- | --- | ---: | ---: |
| Базовый ЛМ | `D:\Program Files\Regime` (фактический путь из MSI/реестра) | `regime`, `yenisei` | `5995` | `5984` |

Его порты всегда читаются из фактических конфигурационных файлов. Они не вычисляются как
«экземпляр №0».

Дополнительные экземпляры устанавливаются отдельными физическими MSI-продуктами:

| Роль | Каталог | Службы | API | CouchDB |
| --- | --- | --- | ---: | ---: |
| Клон 1 | `<корень>\Program Files\Regime1` | `regime1`, `yenisei1` | `6995` | `7984` |
| Клон 2 | `<корень>\Program Files\Regime2` | `regime2`, `yenisei2` | `7995` | `8984` |

Корень установки клона является параметром локального плана. По умолчанию выбирается тот
же том, на котором фактически установлен базовый ЛМ; для текущего стенда это даёт
`D:\Program Files\RegimeN`. Перед подтверждением показываются требуемое место, свободное
место на выбранном томе и ожидаемый рост Windows Installer cache на системном томе.
Пользователь может выбрать другой фиксированный локальный том, но не сетевой путь,
UNC, mapped drive, reparse point или каталог вне `Program Files` выбранного тома.

Между клонами применяется шаг `1000`; переход от базового CouchDB `5984` к первому клону
`7984` является отдельным правилом профиля. Номер клона закрепляется за нормализованным
ИНН и не меняется из-за сортировки, временно отсутствующей ККТ или повторного запуска.

Каждый клон получает уникальные:

- ProductCode, UpgradeCode и PackageCode;
- ProductName и записи Windows Installer/Uninstall;
- каталог установки и RegLocator/AppSearch для `InstallDir`;
- службы `regimeN` и `yeniseiN`;
- Erlang-узлы `regimeN@127.0.0.1` и `yeniseiN@127.0.0.1`;
- API- и CouchDB-порты;
- cookie, созданный штатным custom action.

Клоны не требуют KRS-supervisor. После установки постоянно работают только процессы,
созданные вендорскими NSSM-службами и Erlang runtime.

## 3. Точный профиль исходного MSI

Поддержка версии разрешается только при одновременном совпадении криптографического и
структурного профиля.

| Свойство | Ожидаемое значение |
| --- | --- |
| FileName | `regime-2.6.1-7.msi` |
| ByteLength | `51 007 488` |
| SHA-256 | `68A9633CEFC912C2C1DEFAE40D1C8F433BB794EE66060B822F0895410AB6C5C6` |
| ProductVersion | `2.6.1` |
| ProductCode | `{556FD8AD-43A3-4645-BC54-EBF3043ADF82}` |
| UpgradeCode | `{9449123B-61C4-40DE-AA6C-1BB9AA02EB67}` |
| Authenticode | `Valid` |
| Signer | ООО «Центр развития перспективных технологий» |
| Certificate thumbprint | `6BA5F6BBE4BE27658253C78889334D0E24858C19` |

Структурный профиль дополнительно фиксирует обязательные таблицы, строки Directory,
Registry/RegLocator/AppSearch, Service/custom-action-команды, конфигурационные файлы,
Media/CAB и ожидаемые зависимости между ними. Диагностика сообщает точное несовпавшее
поле без вывода секретов.

Неизвестный MSI никогда не перепаковывается. При этом отказ профиля откладывает только
фазу ЛМ: регистрация ККТ и прямые контроллеры продолжаются.

## 4. Перепаковка и проверка результата

Для работы с MSI/CAB используются официальные NuGet-библиотеки WiX DTF/CAB. DLL входят
в каталог приложения и компактную поставку, но не создают процессов или служб. Код,
бинарники, шаблоны и ресурсы RollingPin в продукт не включаются.

Перед изменением системы программа:

1. проверяет исходный MSI по точному профилю;
2. создаёт защищённый staging с доступом только SYSTEM и Administrators;
3. записывает ownership-журнал до появления копии MSI;
4. создаёт клон только из проверенного источника и детерминированного профиля;
5. повторно извлекает оба встроенных CAB результата;
6. проверяет таблицы, файлы, custom actions и постусловия клона;
7. немедленно устанавливает пакет;
8. удаляет staging в `finally` либо помечает его для точной уборки при следующем запуске.

Исходный MSI содержит `2246` строк File и `2226` строк MsiFileHash. Проверка результата:

- все неизменяемые файлы совпадают с исходными побайтно;
- пять изменяемых конфигурационных файлов совпадают с ожидаемыми байтами профиля;
- FileSize/MsiFileHash меняются только для реально изменённых файлов;
- нет добавленных, потерянных или переставленных файлов/компонентов;
- сохраняются `#media1.cab` с LastSequence `2246` и `#Disk1.cab` с LastSequence `2247`;
- Sequence `2247` (`regime_net_probe.beam`) проверяется во втором CAB отдельно.

В пакете меняются только идентичность продукта, пути/имена экземпляра, порты, узлы,
registry locator и точные custom-action-параметры. Точные quoted service names
`"regime"`/`"yenisei"` заменяются только в подтверждённых позициях профиля.

Отключаются `InstallAutoApdater` и глобальный `StopEPMD` у клонов. Остальная логика
вендорского установщика сохраняется.

## 5. Подпись и граница доверия

Изменённый MSI больше не имеет действительной подписи вендора. Корпоративного
code-signing сертификата и закрытого ключа в проекте и доступных хранилищах нет.
Принят следующий ограниченный риск:

- клон создаётся только локально из точно проверенного подписанного MSI;
- результат не публикуется, не архивируется и не сохраняется в релизной папке;
- результат полностью проверяется до запуска;
- staging защищён ACL и удаляется сразу после установки;
- полевые диагностические архивы исключают MSI и staging;
- ключ подписи не создаётся и не размещается на кассовом узле.

Если впоследствии появится корпоративная инфраструктура подписи, подпись выполняется на
доверенном build/signing-узле, а приложение проверяет корпоративную цепочку. Это не
является условием первой реализации.

## 6. Конфигурация, cookie и секреты

Cookie в `vm.args` создаёт штатный custom action `WriteValuesToVmArgs`. Отдельно
`WriteIniFiles` формирует `local.ini`, а `WriteErtsBinPath` — `erl.ini` с
`Bindir`/`Rootdir`. Программа не генерирует и не передаёт cookie самостоятельно.

Постусловия:

- cookie присутствует в обоих конфигурационных файлах пары `regimeN`/`yeniseiN`;
- внутри пары значения одинаковы;
- между экземплярами значения различаются;
- значение никогда не попадает в UI, журнал, manifest или IPC.

MSI запускается с учётными данными `admin/admin`, пока пользователь не задаст другие.
Полная командная строка `msiexec` не журналируется. `ADMINPASSWORD`, `password`, cookie,
токены и YAML/INI-поля с секретами маскируются до любого диагностического вывода.

## 7. Сеть и Windows Firewall

API ЛМ должен быть доступен второй кассе магазина, поэтому `regimeN` слушает на
`0.0.0.0`. CouchDB используется локально и привязывается только к `127.0.0.1`.

Для каждого установленного экземпляра создаётся принадлежащее приложению правило:

- Inbound Allow, TCP;
- только точный API-порт экземпляра;
- только точный `erl.exe` этого экземпляра;
- профили Domain и Private; Public отключён;
- RemoteAddress по умолчанию `LocalSubnet`;
- при указанном оператором адресе второй кассы — точный IP/CIDR вместо LocalSubnet.

Для CouchDB входящее правило не создаётся. Динамические Erlang distribution-порты
остаются loopback через `inet_dist_use_interface`; фиксировать их диапазон на этом этапе
не требуется.

Программа изменяет и удаляет только правило с точным ownership-id, ожидаемыми полями и
путём. Чужое одноимённое или конфликтующее правило не усыновляется.

## 8. Установка, обеспечение состояния и привязка

Единица планирования ЛМ — уникальный ИНН. Для каждой группы:

1. найти существующий exact ProductCode/ownership либо назначить свободный ordinal;
2. проверить конфликты ProductCode, каталогов, служб, registry locator, портов и firewall;
3. установить базовый официальный MSI либо проверенный клон;
4. дождаться завершения Windows Installer без принудительного завершения чужого
   `msiexec`;
5. запустить `yeniseiN`, подтвердить CouchDB listener и owner path;
6. запустить `regimeN`, подтвердить API listener и owner path;
7. проверить службы, реестр, конфиги, cookie-инварианты и firewall rule;
8. создать/проверить прямые контроллеры всех ККТ группы;
9. отправить привязку endpoint ЛМ в ЕСМ с маскированными credentials;
10. зафиксировать техническую готовность независимо от инициализации ЛМ.

Ошибка одной группы после успешно проверенной основы не отменяет уже готовые группы и не
мешает обработать независимые ККТ. В итогах явно разделяются: регистрация ЕСМ,
контроллер, установка ЛМ, привязка и бизнес-инициализация.

## 9. Жизненный цикл удаления

Удаление клона при работающем базовом ЛМ:

1. проверить ownership MSI-продукта, служб, каталога, реестра и firewall rule;
2. остановить API, затем CouchDB выбранного клона;
3. удалить его MSI стандартным Windows Installer;
4. удалить только его подтверждённое firewall rule и остатки staging;
5. подтвердить, что базовый и остальные клоны продолжают слушать свои порты.

Удаление базового ЛМ при работающих клонах требует отдельной компенсации, потому что
вендорский базовый MSI содержит глобальный `StopEPMD`:

1. штатно остановить все подтверждённые клоны;
2. удалить базовый пакет;
3. дождаться завершения глобального EPMD;
4. запустить CouchDB/API каждого оставленного клона;
5. проверить их порты, owner paths и состояние.

Полное удаление выполняется в обратном порядке: все клоны, затем базовый ЛМ. Данные
удаляются только после отдельного предупреждения. Repair/uninstall проверяются после
удаления staging; нельзя полагаться без теста на кэш Windows Installer.

Legacy KRS-службы и каталоги убираются только elevated-helper после точного совпадения
канонического ImagePath, границы каталога, аргумента supervisor и ownership-манифеста.
При повреждённом ACL восстанавливается точный SYSTEM+Administrators DACL только на
подтверждённом объекте; общий `icacls /reset` не используется. Чужие и вендорские
службы не удаляются.

## 10. Процессы и наблюдаемость

Нормальный экземпляр Erlang создаёт дерево из `erl`, `epmd`, `conhost`, `inet_gethost`,
`win32sysinfo` и вспомогательных процессов. При нескольких ЛМ их количество может быть
заметным. Это штатные процессы вендорского runtime, а не KRS-supervisor.

Критерий отсутствия утечки:

- каждый процесс принадлежит установленному `regimeN`/`yeniseiN` по пути, parent PID,
  командной строке и службе;
- KRS ServiceProvisioner/supervisor постоянно не запущен;
- после штатной остановки пары служб её процессное дерево и listeners исчезают;
- процессы другого экземпляра не прерываются.

Журнал содержит все этапы, точные HRESULT/Win32/MSI-коды, имена проверок и redacted
постусловия. Он не содержит паролей, cookies, MSI с секретными Properties или полных
конфигурационных файлов.

## 11. Совместимость будущих версий

Минимальное обновление ЛМ не должно требовать переписывания приложения. Для новой
версии добавляется локально встроенный exact capability-profile, если совпадает модель
таблиц и адаптер преобразований. При мелком расхождении расширяется адаптер. Новая
архитектура MSI требует отдельного адаптера и явной реализации.

Профили не скачиваются из сети. Неизвестный MSI не блокирует работу ККТ/ЕСМ/контроллеров
и выдаёт точное сообщение, какой fingerprint или структурный контракт не поддержан.

## 12. Стендовая приёмка на рабочем компьютере

Перед первым изменением снимается базовая линия: службы, процессы, listeners, реестр,
установленные MSI-продукты, firewall rules, каталоги и объём `C:\Windows\Installer`.

Обязательная матрица:

1. старт базового `yenisei`, затем `regime`; фактические listeners `5984/5995`;
2. установка базового и одного клона;
3. параллельная работа `regime/yenisei` и `regime1/yenisei1`;
4. проверка путей, Product/Package/UpgradeCode, RegLocator, узлов, cookies и firewall;
5. сетевой доступ к API с разрешённого адреса и отсутствие сетевого доступа к CouchDB;
6. stop/start каждого экземпляра без влияния на другой;
7. install → удалить staging → repair → uninstall;
8. удалить клон при работающем базовом;
9. заново установить клон и удалить базовый при работающем клоне по компенсирующей
   процедуре;
10. повторный запуск без дубликатов и смены ordinal;
11. ошибка/отмена установки одного ЛМ не ломает регистрацию и контроллеры других ККТ;
12. полная очистка с независимым обходом SCM, реестра, процессов, listeners, firewall и
    файловой системы;
13. восстановление исходной базовой линии и удаление всех test-only артефактов.

Перезагрузка проверяется отдельным этапом только после отдельного согласия владельца
рабочего компьютера. До неё реализация не объявляется полностью принятой.

Перед матрицей отдельно проверяется и при подтверждении тестового происхождения удаляется
старый `D:\krs-lm-2.6.1-proof` и ровно его firewall rules. Производственные каталоги
`D:\Program Files\Regime`, `C:\Program Files\ESP` и
`C:\Program Files\KRS\MultiKKT` не входят в автоматическую уборку стенда.

## 13. Тесты и release gates

Реализация ведётся TDD и должна покрыть:

- exact source profile и точные причины отказа;
- трансформацию всех MSI-идентификаторов, каталогов, служб, RegLocator и custom actions;
- проверку обоих CAB и неизменности файлов;
- cookie-, port-, bind- и firewall-постусловия без раскрытия секретов;
- идемпотентность, конфликт чужого ProductCode/службы/правила и стабильный ordinal;
- удаление клона, удаление базового при живом клоне и полную очистку;
- crash-recovery staging и точечную legacy-уборку;
- независимость LM-фазы от регистрации ККТ, контроллеров и инициализации.

Гейт воспроизводит существующую CI-матрицу:

- net8 shared/helper/WinForms tests;
- отдельную net48-компиляцию и полный набор shared-сценариев по CI-скрипту;
- C# 5 сборку с явным `/p:LangVersion=5`;
- MSBuild, найденный через `vswhere` или тот же полный путь, что использует CI;
- `package_compact_release.ps1`, который сам вызывает compact security contract на stage;
- LM safety gate без широкого allowlist для `Process.Kill`, `taskkill` или чужих
  процессов;
- проверку отсутствия MSI, vendor runtime, cookies, паролей и staging в Git/ZIP.

## 14. Критерий готовности

Функция готова к полевой тестовой эксплуатации только после зелёных автоматических
гейтов и полной стендовой матрицы с двумя одновременно работающими ЛМ. До отдельной
перезагрузки статус остаётся `кандидат для полевой проверки`.

Итоговая поставка не оставляет постоянных KRS-служб и процессов, устанавливает ровно
один ЛМ на уникальный ИНН, не зависит от инициализации, позволяет второй кассе обратиться
к API по ограниченному firewall rule и умеет вернуть компьютер к подтверждённой исходной
линии без ручного поиска мусора.
