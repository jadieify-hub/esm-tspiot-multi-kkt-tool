# Экспериментальная массовая регистрация ККТ

> Историческая спецификация этапа регистрации. Текущий полный автоматический режим после этого этапа запускает настройку контроллеров ЛМ ЧЗ по [актуальной multi-INN спецификации](2026-08-26-multi-inn-lm-gateways-design.md); ограничения ниже относятся к самому `BulkRegistrationWorkflow`, а не к координатору всего сценария.

## Цель

Добавить в WinForms-утилиту отдельную экспериментальную кнопку, которая за один запуск находит все физически подключенные фискальные регистраторы, отсутствующие в списке экземпляров ЕСМ/ТС ПИоТ, добавляет экземпляры и регистрирует их.

Существующие четыре кнопки, их обработчики и обычный пошаговый сценарий не изменяются.

## Интерфейс

В блоке действий добавляется одна отдельная полноширинная кнопка:

`ЭКСПЕРИМЕНТ: добавить и зарегистрировать все ККТ`

Перед выполнением программа показывает одно предупреждение и список операций: серийный номер ККТ, номер ФН, ИНН, `port`, `softPort` и `dkktPort`. Операция начинается только после подтверждения пользователя.

Галочка ручной проверки связи с физической ККТ для экспериментальной массовой операции не требуется. Для обычной кнопки регистрации ее поведение остается прежним.

## Получение данных

Массовая операция последовательно выполняет:

1. `GET /api/v1/instances/info` для получения уже созданных экземпляров.
2. `GET /api/v1/dkktList` для получения подключенных физических ККТ и их регистрационных данных.
3. Сопоставление выполняется по серийному номеру: `instances[].id` сравнивается с `kkt[].kktSerial`.
4. ККТ, для которых экземпляр уже существует, исключаются из массовой операции и отмечаются в журнале как пропущенные.

Если любой из двух исходных GET-запросов завершился ошибкой или его ответ невозможно разобрать, массовая операция не начинает изменение конфигурации.

## Распределение портов

Пары портов назначаются по порядковому номеру экземпляра:

- первая ККТ: `50401 / 51401`;
- вторая ККТ: `50402 / 51402`;
- третья ККТ: `50403 / 51403`;
- далее оба значения увеличиваются на 1.

Программа учитывает порты существующих экземпляров и выбирает первую свободную пару. Если первая ККТ возвращается API как `port=50401, softPort=0`, пара `50401/51401` все равно считается занятой.

Индекс пары считается занятым, если существующий экземпляр использует хотя бы один соответствующий порт. Например, наличие `port=50403` или `softPort=51403` резервирует всю пару `50403/51403`. Значения портов вне последовательностей `50401+` и `51401+` не влияют на нумерацию пар, но записываются в журнал как диагностическое предупреждение.

Если существующие экземпляры занимают пары с пропусками, новые ККТ получают свободные пары в возрастающем порядке. Одна пара не может быть назначена двум ККТ в рамках одного запуска.

`dkktPort` берется из соответствующего поля формы и применяется ко всем новым ККТ. Перед запуском он проходит существующую проверку порта.

## Проверка данных

Каждая найденная ККТ проходит существующие проверки:

- серийный номер ККТ состоит из 14 цифр;
- номер ФН состоит из 16 цифр;
- ИНН состоит из 10 или 12 цифр и имеет корректные контрольные цифры;
- назначенные порты находятся в допустимом диапазоне и не совпадают между собой;
- нестандартные префиксы серийников остаются предупреждениями, а не блокирующими ошибками.

ККТ с блокирующей ошибкой данных не обрабатывается. Причина записывается в журнал и итоговый отчет. Предупреждения по всем ККТ включаются в общий диалог подтверждения.

## Выполнение

Новые ККТ обрабатываются последовательно в стабильном порядке, полученном из `/dkktList`.

Для каждой ККТ:

1. Выполняется `POST /api/v1/tspiot` с `id`, `port`, `softPort` и `dkktPort`.
2. Если POST успешен, выполняется `PUT /api/v1/tspiot` с `id`, `kktSerial`, `fnSerial` и `kktInn`.
3. Если POST завершился ошибкой, PUT для этой ККТ не выполняется.
4. Ошибка одной ККТ не прерывает обработку остальных.

Автоматический запуск PowerShell и восстановление Windows-службы при ошибках `1012` или `1013` в массовый сценарий не входят. Ошибка записывается полностью, после чего программа переходит к следующей ККТ.

## Журнал и итог

В журнал записываются:

- начало массовой операции и ответы исходных GET-запросов;
- уже существующие и поэтому пропущенные ККТ;
- план назначения портов;
- начало обработки каждой ККТ;
- полные сведения о POST и PUT через существующий форматтер API-ответов;
- ошибки проверки и API;
- итоговый статус каждой ККТ.

Итоговые статусы:

- `Зарегистрирована` - POST и PUT успешны;
- `Уже существует` - экземпляр был найден до запуска;
- `Пропущена: некорректные данные` - проверка не пройдена;
- `Ошибка добавления` - POST неуспешен;
- `Экземпляр создан, регистрация не завершена` - POST успешен, PUT неуспешен.

После завершения показывается одно итоговое окно с количеством ККТ в каждом статусе. Подробности остаются в редактируемом журнале.

Если POST прошел, но PUT завершился ошибкой, созданный экземпляр не удаляется автоматически. Пользователь может завершить регистрацию штатным пошаговым сценарием.

## Архитектурные ограничения

- Не вызывать существующие обработчики кнопок из массового обработчика.
- Переиспользовать `TspiotApiClient`, парсеры, модели запросов, валидатор и форматтер журнала.
- Вынести расчет плана и портов из `MainForm` в отдельный тестируемый компонент общей библиотеки.
- Не дублировать сериализацию запросов и проверку ИНН/серийников.
- Не изменять контракты текущих четырех кнопок.
- Сохранить совместимость с текущей сборкой .NET Framework для Windows 7-11 и 32/64-разрядных систем.

## Проверка результата

Автоматические тесты должны подтверждать:

- исключение уже существующих ККТ;
- распределение портов с `50401/51401` и увеличением на 1;
- резервирование `51401`, если API сообщает для первой ККТ `softPort=0`;
- пропуск занятых пар и отсутствие повторного назначения;
- отклонение ККТ с некорректными регистрационными данными;
- продолжение обработки плана после ошибки одной ККТ на уровне управляющей логики, если она вынесена из формы.

Ручная проверка должна подтвердить, что новая кнопка помещается в компактной форме, обычные кнопки работают без изменений, подтверждение содержит полный план, а журнал автоматически прокручивается к последней записи.
