# Происхождение контракта привязки ЕСМ к ЛМ ЧЗ

**План составлен:** 2026-08-26

**Публичный источник повторно проверен:** 2026-08-27

**Область:** только HTTP-контракт привязки уже зарегистрированного экземпляра ЕСМ к уже готовому контроллеру ЛМ ЧЗ. Создание и конфигурация Windows-служб сюда не входят.

## Подтвержденный внешний контракт

| Факт | Официальный публичный источник | Внутреннее имя проекта |
| --- | --- | --- |
| Метод и путь: `PUT /api/v1/settings/lm/{id}` | CSI, раздел «Настройка ЕСМ», шаг 6 | `TspiotDefaults.LmSettingsPath`, `ConfigureLmGatewayAsync` |
| `id` обозначает идентификатор экземпляра ЕСМ; в описанном процессе он задается равным `kktSerial` | CSI, раздел «Настройка ЕСМ», шаги 3–6 | `InstanceId`, `KktSerial` |
| JSON-поле `address` имеет тип string | CSI, пример тела PUT | `LmConnectionRequest.Address` |
| JSON-поле `port` имеет числовой тип | CSI, пример тела PUT | `LmConnectionRequest.Port`, `ControllerGrpcPort` после отдельного compatibility gate |
| JSON-поля `login` и `password` имеют строковый тип | CSI, пример тела PUT | только короткоживущие credentials непосредственно перед PUT |
| Метод read-back: `GET https://localhost:<softPort>/api/v2/info` для ЕСМ 1.6.3+ | «Руководство по интеграции ЕСМ для разработчиков ПМСР», версия 1.9 от 25.08.2026, передано владельцем проекта | `TspiotDefaults.LmInfoPath`, `GetLmInfoAsync` |
| Корневая идентичность ответа: `kktSerial`, `kktInn`; блок `lm` содержит endpoint самого ЛМ ЧЗ (`ip`, `port`), `status`, `version` | то же руководство, описание и пример ответа `/api/v2/info` с портом ЛМ `5995` | `LmGatewayInfoParser`, безопасная `LmGatewayInfo` |

Источник: [«SetRetail10 — Установка и настройка ТС ПИоТ»](https://crystals.atlassian.net/wiki/spaces/SR10SUPPORT/pages/6404898850/SetRetail10), публичный портал поддержки продуктов CSI.

Смысл `address` и `port` в официальном шаге — адрес и порт сервера ЛМ ЧЗ с контроллером ЛМ, к которому настраивается связь ЕСМ. Имя `ControllerGrpcPort` является термином этой реализации; фактический тип слушателя и его совместимость должны быть отдельно подтверждены процедурой service-provisioning, а не выводиться только из примера порта.

Официальный пример использует имя заголовка `ContentType`. Реализация отправляет стандартный HTTP-заголовок `Content-Type: application/json; charset=utf-8`; это транспортное исправление синтаксиса примера, а не дополнительное vendor-specific поле.

## Что публичный источник не подтверждает

Публичная инструкция CSI **не подтверждает**:

- API удаления или очистки LM-настройки экземпляра ЕСМ;
- безопасную повторяемость PUT после timeout, разрыва соединения или потерянного HTTP-ответа;
- read-back, который доказывает фактическое применение настроек после ответа 2xx;
- создание нескольких Windows-служб контроллера ЛМ;
- отдельный data/config path, второй локальный порт, формат профиля, service account, dependencies или recovery actions;
- возможность копировать штатный профиль, секреты, сертификаты или другие данные официальной службы.

Переданное официальное интеграторское руководство закрывает только пробел read-back для текущей ветки ЕСМ 1.6.3.x. Поэтому успешный HTTP-ответ без последующей сверки называется `BindingAccepted`; статус `BindingVerified` появляется только при совпадении `kktSerial`, `kktInn` и endpoint целевого ЛМ ЧЗ из `lm.ip`/`lm.port` в `/api/v2/info`. Видимый endpoint без локально заданного ожидания получает отдельный статус `BindingObserved`. Поля `lm.ip`/`lm.port` не являются gRPC/REST-портами локальной службы контроллера. Потерянный PUT не повторяется автоматически и требует `RequiresAttention`. Остальные служебные и профильные факты могут использоваться в частной ветке только после `TechnicalCompatibilityReady`; их публикация отдельно требует `PublicSourceReady`.

Read-back вызывается только по HTTPS со штатной проверкой цепочки сертификата Windows. Транспорт отдельно классифицирует отказ доверия сертификату, чтобы интерфейс предлагал установить авторизованный корневой CA ЕСМ. Пользовательский callback, `ServerCertificateCustomValidationCallback`, режим accept-all и любой иной обход проверки сертификата не применяются.

Руководство не добавляется в репозиторий. Ответ `/api/v2/info` содержит также credential-поля `login`, `pass` и `token`: `pass` и `token` маскируются сразу после HTTP-ответа, а тип `LmGatewayInfo` намеренно не имеет ни одного credential-поля.

## Граница независимой реализации

Архив стороннего ПО `RollingPinForESM.zip` не является источником имен, кода, пользовательского интерфейса, сценариев, формата конфигурации или служебных параметров этого проекта. Его содержимое повторно не исследуется.

Разрешенные основания реализации:

1. официальный публичный HTTP-контракт CSI, указанный выше;
2. публичные стандарты HTTP, JSON и Windows API;
3. самостоятельно спроектированные модели и имена `LmGateway*`;
4. для будущих служб — собственная black-box-характеризация официального пакета в Sandbox, публичные Windows API и разделённые technical/publication gates второго плана.

## Gate создания Windows-служб

Проверка официальных публичных источников от 2026-08-27 сохраняет `PublicSourcePending`: в них нет полного multi-instance-контракта. Этот статус блокирует public-публикацию, но больше не блокирует техническую характеризацию в private-ветке.

Официальный установщик `1.6.3.2` исследован только black-box в одноразовых Windows Sandbox. Два чистых прогона подтвердили supervisor-изоляцию через отдельный process-local `ProgramData`; третий контроль подтвердил, что пустой профиль не требует копирования CA, сертификатов или ключей. Статус версии — `TechnicalCompatibilityReady`, поэтому private-реализация создания, обновления и удаления служб разрешена. Полные условия, evidence digests и граница публикации находятся в [compatibility gate](2026-08-26-official-lm-controller-compatibility.md).

Вывод `PrivateBlackBox` не меняет публичный HTTP-контракт привязки: supervisor, exact-version capability profile, минимальная схема конфигурации и служебные параметры остаются отдельным private service-provisioning слоем. `PublicSourcePending` по-прежнему запрещает публикацию кода или сборки с этими фактами.

Уже реализованная привязка и её read-back для заранее подготовленных контроллеров остаются независимыми от обоих gate.

## Дополнение read-back — 2026-08-28

Исторический Phase 1 ниже проверял только PUT и потому корректно запрещал синтезировать `Verified` из ответа 2xx. После получения руководства ЕСМ 1.9 добавлена отдельная доказательная операция: `GET /api/v2/info` на softPort конкретной ККТ. Старый вывод сохраняется для одного PUT; новый статус `BindingVerified` требует отдельного совпавшего read-back.

Документ и тестовые фикстуры не содержат реальных `login`, `password`, ИНН, серийных номеров, адресов организации или иных эксплуатационных данных. План и результаты привязки не хранят credentials; пароль маскируется до диагностических и журнальных границ. `login` намеренно не входит в общий список секретных ключей и в будущем UI не должен записываться в долговременное состояние.

## Phase 1 review — 2026-08-27

**Проверенный commit:** `8635afa` (`Закрыть утечку Bearer-токена в журнал`), включая реализацию от `5b62ed6` до `2834762`.

Итоговая матрица:

- shared-тесты .NET 8: 96/96;
- shared-тесты .NET Framework: 96/96, системный C#-компилятор с предупреждениями как ошибками;
- Legacy WinForms: Release-сборка прошла с предупреждениями как ошибками;
- Modern WinForms: Release-сборка прошла, 0 предупреждений и 0 ошибок.

Во время ревью найден и исправлен один блокирующий дефект общего маскировщика: строка `authorization=Bearer <token>` могла оставить часть токена после пробела. Исправление и регрессионный тест входят в `8635afa`. Других блокирующих замечаний после повторной матрицы и статического аудита нет.

Подтверждено:

- реальный пароль существует только в короткоживущем credential/HTTP DTO и не входит в план, результат или прогресс;
- LM PUT сериализуется один раз, а `ApiResponse.RequestBody` получает отдельную маскированную копию;
- discovery не вызывает `/dkktList`, а последовательно читает только зарегистрированные экземпляры;
- сопоставление строится по точному 14-значному серийному номеру ККТ, а не по ИНН;
- одинаковый локальный endpoint блокирует все конфликтующие строки;
- ответ 2xx называется `BindingAccepted`, а не подтвержденной настройкой;
- после потерянного ответа PUT автоматически не повторяется и возвращается `RequiresAttention`;
- код этапа не зависит от WinForms, Windows-служб, PowerShell, recovery-сценария или стороннего архива;
- README и пользовательский интерфейс на этом этапе не изменялись.

Отклоненные варианты: regex-only разбор JSON-секретов, автоматический повтор PUT после timeout, использование ИНН как ключа ККТ, статус `Verified` только по ответу 2xx и раннее связывание с логикой Windows-служб.

**Граница следующего этапа:** Phase 1 готов как безопасный shared-фундамент. Black-box-характеризация `1.6.3.2` завершена со статусом `TechnicalCompatibilityReady`; production-код supervisor/helper можно реализовывать только в private-ветке. Public-публикация дополнительно требует `PublicSourceReady`.
